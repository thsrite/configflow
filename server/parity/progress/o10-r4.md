## 做法与正确性论证

### 直接投影（缓存关时的路径，也是缓存未命中时的计算）

- `redact.decodePublic`：原来每一层都 `json.Valid` 扫一遍子树再逐成员 `Decode(&RawMessage)`，嵌套 d 层的字节被扫 ~2d 次。
  改为一次 Token 遍历建出同样的树（对象 `orderedFields`，重复键保留首位置、取末值；数组 `[]any`；数字 `json.Number`）。
  超过访问深度上限（128+2）的值仍留 `RawMessage`，访问时照旧 Redacted。整体非法 JSON 照旧返回标准错误。
  `fieldValue`（只取一个成员）保留只解顶层，避免对整份 system_config 全解码。
- `PublicDeploymentMessagesModel`：原来 `copyDeployment`（整条编码+解码）后 `SetJSON`。`SetJSON`/`Clear` 本身是 COW，
  所以改成结构体浅拷贝；两个调用方（公开投影、deploy 适配器）都只编码结果。注释写明结果与输入共享嵌套值。
- 公开投影的 `deployments`：原来把编码后的历史再 `jsondecode` 成 map、每条再解码成 `model.Deployment`。现在直接遍历
  类型化 `Map`：有效条目用其值；无效条目取原始 token 走原规则（非对象 → null，对象 → 解码）；有重复 id 时整体走原编码路径
  （Go map 解码取末值）。输出仍是 `json.Marshal(map)`（键排序），与原来一致。
- `deploy.ContentView`：非空类型化历史原地读（条目、`EntryValid` 与解码编码结果相同）；空/null/缺失/类型错误时仍读
  `MemberJSON` 判断（此时很便宜），错误语义不变。
- `deploy.BorrowedTarget`：与 `NewTypedTarget` 同样抽字段，但 `Record` 直接用借来的记录。checker 在后台比对前
  `SnapshotTarget` 深拷贝；`Status` 路径只读。其他调用方仍用 `NewTypedTarget`。

### 派生视图缓存（`internal/api/agents/agent_view_cache.go`）

条目只由这些输入决定，键里全都有：

| 输入 | 键 |
|---|---|
| 存储的 Agent 记录、配置（内容源）、默认 profile | store head（`BorrowAgentsAt` 与记录同一次读取得到）+ 注册表位置 + id |
| 心跳 overlay（7 个运行时字段、last_heartbeat、status） | 每次读都对 overlay 后的这 9 个成员算 sha256 指纹；心跳不改 head 也会立即失效 |
| 离线判定（依赖当前时间） | 判定在读时做、写进 status 后才算指纹，所以时间推进导致的离线立即生效 |
| `AGENT_REGISTRATION_KEY`（凭据收集总会加入） | 环境变量值 |
| 视图（全量/summary） | mode |

- 只保留一代（head 变化即清空），每个 Agent 每种视图一条。写事务内的读（`Shared=false`）从不缓存。
- 缓存的是 `SanitizeCredentials` 之后、`content_sync`/`has_update`/`upgrade_available` 之前的 map；返回调用方的是
  `maps.Clone`。`content_sync`（checker 状态、TTL、后台任务）、`has_update`、`upgrade_available`（磁盘上的升级文件）、
  HTTP 出口的 token 脱敏每次请求都算。
- summary 的凭据种子（含历史的存储记录整编码后收集）按 (head, 位置, id) 单独缓存，与 overlay 无关。
- 内容源按 (head, profile) 缓存；只缓存成功和 `repo.Error`（缺 profile），其他错误不缓存。
- 内存：一代 3 个 Agent ≈ 响应大小（~0.4 MB）。

### 缓存关（直接计算）剩余拆解（`r4-off` route profile，allocs 差分 cum）

`GET /api/agents`（≈75 MB）：
- `publicAgentWithCredentialsModel` 61%：其中整条 `model.Marshal(record)` ≈27%（`EncodeRecord`），`publicDeploymentsModel` 21%
  （`PublicDeploymentMessagesModel` 14%：事件 `json.Marshal` → `SetJSON` 再解码成类型化事件 → 再编码；`Deployment.MarshalJSON` 13%），
  `SanitizeCredentials` 19%（树解码 + 两遍访问 + 编码）。
- `loadContentSource` 20%：`Repository.Config`（`resolveConfig` 复制 profile）10% + `model.Marshal(config)` + `SourceFromJSON`（`DecodeConfig`）。
- HTTP 出口 `jsonresp.Encode` + token 脱敏 16%（与 Python 的 `jsonify` + 脱敏相当，所有路由共有）。
- 根因仍是 model 编解码放大（编码 38 B/B、解码 147 B/B，R5/S3）。R5 后直接计算预计还能降一半以上，但追不上 Python 的 24 ms，
  所以这 4 条路由的验收依赖缓存（命中时 0.5–6 MB）。
`GET /api/agents/<id>`：同构，`loadContentSource` 占 42%（单 Agent 也要解一整份配置），投影 45%。
`summary=1`：凭据种子（含历史整编码 + 收集）61%，投影 32%。

`/api/profiles` 剩余 1.1–1.3 ms / 0.11 MB 是每个请求共有的固定开销（JWT、`View` 读 head、出口脱敏），不在 bindings。

## 剩余 / 建议

- R5（model 编解码）做完后重测缓存关一列；若直接计算仍慢于 Python，缓存保留。
- `loadContentSource` 每请求每 profile 一次 `Config` + 编码 + `DecodeConfig`；R2（Config 借用）后可以直接 `SourceFromConfig`，
  省掉一次编码和解码（这次没做：跳过 `DecodeConfig` 需要证明与往返等价，留给 R2 合批后）。
- push-diff / entries 路由仍用 `NewTypedTarget` 两次，可同样换 `BorrowedTarget`（不在本任务测量范围）。
