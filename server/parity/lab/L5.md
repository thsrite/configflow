# L5 实机测试：路由器 R04/R05/R07–R14（实验 RouterOS CHR 与实验 iKuai）

- 执行：O16 / L5，Opus，2026-11-21–22，分支 `go-audit-lab`。面板沿用 CT 220（当前分支 Go 面板，开启登录）。
- RouterOS：L4 建的 CHR VM 233（7.25.1，镜像来自 download.mikrotik.com，SHA256 已核对）。WAN ether1 10.97.0.133 在 cfgt，LAN ether2 192.168.94.1/24 + IPv6 在隔离网桥 cfl4。LAN 上的 Mihomo 主机 CT 234（192.168.94.10）作为代理网关 Agent。
- iKuai：PVE 上已有的 `ikuai-4.0.314.iso`。
- 新 guest 登记在 `/root/cf-gwip-lab/l5-owner.json`；沿用 L4 的 233/234/235 登记在 l4-owner.json。

## 计划

来源：review-r04/r05/r07–r14 的 L5 节、设计 §6.7，以及 L4 移过来的 I6。每个模块先在真机上跑通主流程，再做最有代表性的故障场景；做不了的写明原因。

| # | 模块 | 场景 | 判定 |
|---|---|---|---|
| L5-1 | R04/R12 | 选 IP 规则集（静态路由经 Mihomo），probe → plan → apply；再次 plan 应为无变化 | 设备上的路由与计划一致，注释带归属标记；第二次 plan 无变化 |
| L5-2 | R08 | 切到策略路由（来源策略）再切回静态，最后回滚 | 私有路由表、规则与地址列表正确；切换和回滚后 LAN/WAN NAT 不受影响 |
| L5-3 | R07 | 开启回流（return routing） | 地址列表、NAT 免转换按计划写入；关闭后清理干净 |
| L5-4 | R09 | DNS 守护（Netwatch 劫持） | Netwatch up/down 时劫持 NAT 正确启停 |
| L5-5 | R10 | IPv6 路由（规则集 IPv6 目的） | 路由写入与回读一致；回滚后不误报「被外部修改」 |
| L5-6 | R11 | PD 守护 | 实验网没有 DHCPv6-PD 上游，预计只能验证脚本和计划任务的写入与撤回 |
| L5-7 | R14 | 规则自动同步：内容增删两次；规则源无响应；同步中 SIGTERM；手动发布与立即同步并发 | added/removed 正确；失败按间隔重试；关机后无设备写入；后到者 409 |
| L5-8 | R12 | 发布到第一项写入时 SIGTERM 面板 | 重启后 `last_release` 显示中止，预览能接上 |
| L5-9 | R04 | HTTPS 自签证书（校验开/关）；只读账号、缺 `rest-api` 的账号 | 握手与证书校验符合设置；权限不足给出明确提示 |
| L5-10 | R04/R07 | 批量写入中途切断管理链路 | 10 s 后记为不确定，按回读收敛，不误删外部对象 |
| L5-11 | R13 | 关联同一 Agent 的路由器提醒（pending/synced/blocked） | 与「预览发布」一致 |
| L5-12 | R05/R12 | iKuai：发布静态路由与回流；删除后 ID 是否复用 | 设备与计划一致 |
| L5-13 | A23 I6 | 同一 ROS 两条连接时 IPv6 prepare 与 R14 规则同步并发 | 409 BUSY 或串行，不死锁 |

## 结果

| # | 结果 |
|---|---|
| L5-1 | 通过：probe 识别 routeros 7.25.1（routes/nat_bypass/address_sets）。选 Telegram IP 规则集后 plan → apply：设备上 7 条 IPv4 路由（6 条 `cf-Telegram`，1 条 `cf-fake-ip` 198.18.0.0/16），下一跳 192.168.94.10；默认配置空间开了 Mihomo IPv6 + `fake-ip-range6` 后，还写入 4 条 IPv6 规则集路由（`cf-rule6:<router>`）和 IPv6 Fake-IP 路由（`cf-fakeip6:<router>`），下一跳是 Mihomo 的链路本地地址。读回与计划一致，再次 plan 为空。只开 IPv6 不填 `fake-ip-range6` 时，plan 被阻止「IPv6 Fake-IP 配置无法确认…fake-ip-range6 必须填写有效的 IPv6 网段」。关掉 IPv6 后发布撤回，设备上的 IPv6 受管路由全部删除 |
| L5-1b 管理地址保护 | 通过：IPv6 Fake-IP 受管期间修改管理地址被拒「请先关闭 IPv6 Fake-IP 并发布撤销，再修改路由器类型或管理地址」 |
| L5-2 策略路由 | 通过：需要先在「客户端设备」里设一个智能分流地址（否则计划阻止「请先在「当前配置 → 客户端设备」中把至少一个 IPv4 地址或网段设为智能分流」）。切到来源策略：私有路由表 `CF_Proxy_Routing_01`、mangle（prerouting jump + return + mark-routing）、源/目的/绕过地址列表，6 条受管主表路由迁入策略（fake-ip 路由仍在主表），策略视图逐项 `matched`。切回静态：重建 6 条静态路由，策略对象全部删除，再次计划为空 |
| L5-3 回流 | **失败，发现两个缺陷**。(a) 管理地址是 WAN 口（10.97.0.133）时，计划给出「路由表 104 → 10.97.0.133」，不阻止；apply 时 Agent 报「主路由 10.97.0.133 不在 eth0 的网段 192.168.94.0/24 内」，按逆序撤销、设备干净（L5-D2）。(b) 管理地址改成 LAN 口 192.168.94.1 后，Agent 在 Debian 12 主机上写入回流资源，但写入后的认领比对失败「写入后的资源内容与计划不一致；安全撤销未完成，未删除无法确认归属的资源：nft 表 configflow_return 存在未知或发生变化的对象」：残留 ip rule、路由表 104 和 nft 表，之后每次计划都被「上次回流事务未完成，不能重新分配资源」挡住，Agent 的 DELETE 也拒绝（「无法证明旧回流资源的归属」），只能人工清理（L5-D1） |

| L5-7 R14 | 规则源用实验网内可控的 YAML `payload`（LabIP，公网 /24 测试网段，报告不列具体网段）。(a) 加 1 个网段 → 同步 `+1`，日志「新增 …」；删 1 个网段 →「立即同步」`-1`，日志「删除 …」，设备一致；相邻网段在手动计划里合并为 /23。缓存刷新会立即触发一次同步；`rule_sync_interval` 单位是分钟。(b) 规则源不响应（面板 CT 内丢弃到 :8090 的连接）→ `failed`「远程规则下载失败：exception_type=ConnectTimeout status=0」，自动同步仍开启（没有暂停）；恢复后同步成功 `+1`。(c) 同步中 SIGTERM：同步是批量写入，30 条在看到第一条新路由时已写完；SIGTERM 等同步结束才退出，记录完整（`+30`，synced），中途打断没测到。(d) 手动发布与「立即同步」同时触发：后到的同步 409「此路由器正在发布或同步，请稍后重试」，发布成功后基准为 synced。外部规则源（GitHub 上的 Telegram）在实验网下载失败时整次同步失败，所以 R14 只保留 LabIP。JSON 形式（`{"payload":…}`）的规则源被路由器路径拒绝（与 Python 相同的严格分类），手动计划对它给出 0 条路由且没有提示，记为 L5-O1 |
| L5-9 R04 | HTTPS 自签证书：校验开 → 502「无法连接 RouterOS：SSLError」；校验关 → 正常。缺 api/rest-api 权限的账号 → 502「RouterOS 认证失败，请核对…检查用户组的 api、rest-api 权限」。只读账号（read,api,rest-api,test）probe 成功；写入被拒的提示没测到（计划为空 / 同步进入「来源、规则选择或网关设置尚未发布」暂停） |
| L5-12 iKuai | iKuai 4.0.314（PVE 上已有的 ISO，控制台装机），LAN 192.168.94.2。probe：`ikuai` 4.0.314，能力 routes/nat_bypass/address_sets/policy_routes。plan → apply：5 条静态路由（`cf-LabIP`/`cf-fake-ip`）、NAT 免转换 IP 分组 `cf_nat_1` 和规则，复查计划为空。删除 1 个网段 → 删除对应路由；再新增 → 新路由 ID 为 6，**删除的 ID 2 没有复用**（R05 第 10 项）。路由列表对每条受管路由都提示「路由字段与已验证的 iKuai 4.x 格式不兼容，无法保留完整配置（未知：dst_addr_int,gateway_int）」并标为不可编辑：这个固件多返回两个整数字段，不影响发布和删除（L5-O2）。删除路由时 NAT 免转换分组没有立刻收窄（摘要显示更新后分组「现 6 个」，期望 5 个），复查计划为空，像是有意的延迟收窄，没能直接读设备核实（L5-O3） |
| L5-8 iKuai 长批次中断（R12 第 4 项） | 320 个网段（324 个操作）发布到 iKuai，写到 57 条时 SIGTERM：宽限期内继续写到 106 条后停止，进行中的 apply 请求被断开。**重启后 `last_release` 仍显示上一次成功的发布**，这次中断没有留下记录（L5-D3）；重新计划列出剩余 223 条新增，没有阻止项，可以接着发布 |
| L5-1c 忙碌保护 | 规则缓存刷新触发同步期间，修改路由器和 probe 都返回 409「此路由器正在发布或同步，请稍后重试」 |

## 缺陷

| ID | 严重程度 | 摘要 | 建议 |
|---|---|---|---|
| L5-D1 | **高** | 回流在 nftables 1.0.6（Debian 12 bookworm）主机上无法启用，且留下无法自动清理的残留。原因：`desiredReturnNFT`（`backend/agents/go-agent/routes/return_routing_owned.go`）给表和链都加了 `comment`，`confirmResources` 用它和 `nft -j list` 的回读逐项比较；nft 1.0.6 的 JSON 不输出表和链的 comment（规则的 comment 会输出），于是认领必然失败，owner.NFT 为空且 pending。之后 `checkReturnResources` 看到「未知对象」，计划和撤销都被阻止。测试服务器上的 nft 版本较新，自动化测试没有暴露。Python 时代同一个 Agent，不是 Go 回归 | Agent：比较表和链时，回读缺少 comment 键就忽略 comment（用名字和 token 识别归属），或者先探测 nft 是否回显表和链的 comment；对 pending 且对象与期望完全一致的状态允许继续认领或撤销。在 Debian 12（nft 1.0.6）容器里加回归测试，并升级 Agent 版本 |
| L5-D3 | 低 | iKuai 长批次发布被 SIGTERM 打断后，`last_release` 仍是上一次成功的记录，界面看起来「上次发布成功」，而设备只写了一部分（重新计划能接上，没有安全问题） | 发布开始时先落一条「进行中」记录，关机宽限期结束前把它改成「已中止」，与 R12 F2 对 RouterOS 的要求一致 |
| L5-D2 | 低 | 路由器管理地址不在 Mihomo 所在网段时（例如经 WAN 口管理），回流计划把管理地址当下一跳，计划不阻止，apply 时才失败（会撤销干净） | 计划阶段校验下一跳是否在 Mihomo LAN 网段内，或从路由器上读取它在该网段的地址作为下一跳 |

## 观察

- L5-O1：路由器自动同步对规则源做严格分类，以 `{` 开头的 JSON 形式（`{"payload":…}`）会被拒绝（与 Python 相同）；同一个规则源 Mihomo/MosDNS/OxiDNS 都能用（A11 F1）。手动计划对这种规则源给出 0 条路由，没有任何提示。文档网段（TEST-NET）按设计被忽略。
- L5-O2：iKuai 4.0.314-beta（2026-10-13 构建）的静态路由多出 `dst_addr_int`、`gateway_int` 字段，受管路由在路由列表里显示为不可编辑。
- L5-O3：iKuai NAT 免转换分组在删除路由时没有立即收窄（见 L5-12），需要复核是否为有意的延迟收窄。
- L5-O4：规则缓存刷新会立即触发一次路由器同步；`rule_sync_interval` 单位是分钟；同步期间修改路由器、probe 都返回 409。

## 没有覆盖到的

- R09 DNS 守护（Netwatch 劫持）：需要 LAN 上再装一个 OxiDNS 作为 DNS Agent，时间原因没做。
- R11 PD 守护：实验网没有 DHCPv6-PD 上游。
- R13 路由器提醒、R08 F1/F6（成员换表、策略发布中 SIGTERM）、R10 补偿 DELETE 回复丢失、R04/R07 批量写入中途切断管理链路、L4 移过来的 I6（IPv6 prepare 与 R14 并发）：没做。
- 写权限被拒的提示（只读账号写入）：没走到写入路径。
- R14 同步写入中途打断：批量写入太快，没打在中途。
- 「完整 TUN」主路由分流（L4 移过来）：没做。

## 环境与清理

- 实验路由器：CHR VM 233、iKuai VM 236；Mihomo 主机 CT 234、客户端 CT 235 在隔离网桥 cfl4 上。CHR 上的实验配置（证书、`cf-ro`/`cf-norest` 用户组和账号、LAN 侧 NAT）只存在于这台 VM。
- 本批顺带在 PVE 宿主机上执行过一次 `nft add table inet cf_probe_t` + `nft delete table`（核对 nft 1.1.3 的 JSON 输出，空表，立即删除），宿主机其他规则未动。
- 结束时销毁全部 L2–L5 实验 guest（CT 220、221、234、235，VM 233、236），删除 cfl4 网桥，并把 `inet cfgt` 表恢复为 L2 之前的规则（去掉指向 CT 220 的 DNS 重定向，否则其他实验 guest 的明文 DNS 会失效）。生产 guest 和其他工作的 CT 240 全程未碰。
