# L3 — 规则同步、DNS 联动与 DNS HA 实机计划

状态：待 A18 独立 Opus HR 复核后，由协调者安排实验网执行；本次移植未操作实机。
按 WORKFLOW 的 L3 授权与隔离规则执行，所有对象必须是登记在 owner 文件中的新实验设备。

1. 两台独立原生主机（systemd/OpenRC 各一）开启 HA：备机先同步配置，再同步主机，最后按备机→主机应用 keepalived；两端 stored state / journal 均 succeeded 后路由器才使用 VIP。
2. 用连续 DNS 查询记录丢包和切换时间。关闭主机、恢复主机，验证备机接管和正常抢占；分别验证原备机已持有 VIP 时从任一成员发起完整发布。
3. 完整配对发布：新备机成功并健康 → 原持有者让位 → 两端连续两次确认唯一 VIP 和 VIP DNS → 原持有者候选上传/激活 → 撤销让位 → 主机重新持有 VIP。规则热更新必须保持 reload_only，无核心重启。
4. 在让位 POST、原持有者上传、让位 DELETE 后丢弃响应；面板依次 SIGTERM、kill -9 并重启。确认原 ID、日志与 payload 继续使用，已受理上传不重复，交接未确认时不更新原持有者，不提前释放配对预留。
5. 停机分别落在 keepalived 备机应用后、主机应用后、双端记录最终提交前。重启后按同一 spec 幂等继续，两端记录不会半开启；并验证 D-A18-1：HA 锁忙保持 applying，下一轮重试。
6. 主机 keepalived 应用失败：按反序恢复旧 spec / 移除首次配置。注入撤销失败，确认 leftover 成员记录、failed 状态和停用清理；离线成员停用返回 can_force，强制后按提示人工清理实验设备。
7. Docker host/macvlan 分别验证跨宿主环境证据；相同宿主、相同 boot ID、缺失实时身份及 bridge 网络必须在核心写入前拒绝。暂存完成后更改环境证据，再激活也必须拒绝。
8. A16：真实 Mihomo provider 刷新、OxiDNS paths 选择性下载及旧 Agent 回退；结构变化配对只重载发布。两个成员的规则 worker 不得创建重复配对任务，库关闭时保留基线字节。
9. A17：Mihomo 监听变化 → HA OxiDNS 双端更新并同步草稿；相同地址不上传，联动仅允许 network。来源继续发布、上传应答丢失、草稿提交后停机都应收敛，签名继续有效。
10. 双端 health 异常、split/no holder、VIP DNS 不健康与旧 Agent 无 handoff 协议：必须保留未更新主机，暴露状态。激活 staged pair 前重新读取实际 VIP 持有者。

11. （复核新增）主机候选激活失败（Agent 回滚）后两台一新一旧：VIP 分别位于主机/备机时查询对比，确认 DNS 不中断、差异只来自配置；再发布一次后两台最终配置摘要相同。
12. （复核新增，供 review-a18 O-1 决定）交接确认后新持有者永久断网，或让位后原持有者断网 10 分钟：记录 journal 状态、停用与推送的返回、VIP 位置与 dig 结果；恢复后应自动收敛。
13. （复核补充）第 2 项用 `poweroff -f`/断电模拟主机宕机，第 3 项同时比对两台最终 `config.yaml` 摘要；停用中途（备机 DELETE 后）`kill -9` 面板，记录路由器仍发 VIP 期间客户端解析情况。

验收报告须区分实验网实际 DNS 连续性与本轮 loopback/Runtime 自动化结果；结束后按实验网流程清理或登记留用设备。

## L3 缺陷

| ID | 严重程度 | 摘要 | 建议 |
|---|---|---|---|
| L3-D3 | 低 | HA 成员的规则自动同步失败时，状态只有「规则自动同步失败；将稍后重试，可查看设备发布状态」，日志只有「Agent rule sync failed (*dnsha.Error)」，看不到原因；同一原因在手动「更新规则」里会明确提示「请先完整发布相同的主备配置，再更新规则」。用户不知道要先完整发布一次 | rulesync 遇到 dnsha 的用户错误（`IsUserError`）时，把该中文消息写入状态并记日志 |
| L3-D2 | 中 | HA 成员的配对发布 `rollback_failed` 后，在 Agent 页点「重新恢复」：设备恢复成功，但面板的 GET 走 `dnsha.PairDeployment`。配对日志仍把这台的 child 指向该发布，于是只推进配对，再用发布汇总覆盖状态，**从不向 Agent 查询**，存储的任务停在 `rolling_back`，这台的发布一直被 409 拒绝。Python 的 `oxidns_ha_publish.deployment` 逻辑相同（Python 就有）。绕过办法：停用 HA 后再发布 | 在配对日志已到终态、而成员任务是非终态（恢复之后）时，GET 先走 A01 的 `ReadDeploymentModel` 向 Agent 查询并记录，再汇总；或者对 HA 成员的 recover 由配对流程接管。附真实 Runtime 的回归测试 |
| L3-D1 | 中高 | OpenRC（Alpine）成员停用 DNS HA 后 keepalived 残留并持有 VIP。`removeOxiDNSHA`（`backend/agents/go-agent/routes/oxidns_ha_resources.go`）先删 `keepalived.conf`，再调 `haRestoreService`；Alpine 的 init 脚本有 `required_files=$cfgfile`，配置删除后 `rc-service keepalived status/stop` 都失败，`haServiceRunning` 于是认为服务没在运行，不执行 stop，也不报错，停用返回成功。后果：VIP 一直留在这台；用同一 VIP 再次开启时被拒（409「虚拟 IP … 已在本机网卡上，但不是由 DNS 高可用持有」）；用户手工 kill 后 OpenRC 状态变成 `crashed`，再次开启失败「keepalived 启动后未保持运行」，必须 `rc-service keepalived zap`。开启时也能看到同一原因的噪声：配置写入前 keepalived 被拉起 4 次，报「keepalived.conf is not readable」 | Agent：停用时先停服务（或按 pidfile 停），再删配置；`haServiceRunning`/启动时识别 OpenRC 的 `crashed` 状态并先 zap。需要升 Agent 版本，并附 OpenRC 的回归测试（L1/L3 的 Alpine 容器即可） |

## L3 观察

- L3-O1：面板 `kill -9` 后，到下一次心跳之前（≤ 约 1 分钟），Agent 显示离线，HA 状态 health `down`，规则同步「等待设备上线」。心跳状态只保存在内存，与 Python 相同；SIGTERM 不出现这种情况。
- L3-O2：`-ha-check` 只检查本机是否应答（WAN 故障时的 SERVFAIL 也算健康），单台上游故障按设计不迁移 VIP；VIP 在上游已坏的那台上会持续解析失败。这是有意的取舍（避免上游抖动导致切换），但值得写进文档。
- L3-O3：配对发布的移交确认时间窗是 30 s（`HandoffTimeout`）。实验网做了十几次配对发布，有一次超时，原因没查清（当时主机旧配置查询保留名约 600 ms）。超时后状态正确（一新一旧、原主机未更新），完整发布再重试即可恢复。
- L3-O4：URL 型规则库条目的上游内容变化不经过 A16（设备侧 http provider 按自身 interval 刷新，OxiDNS 要等下次发布或「更新规则」）。
- L3-O5：A17 联动失败消息直接拼接内部英文（「Preparation interrupted before upload; current service unchanged」）；发布页对同一原因显示的是中文「发布在上传前中断，设备上的服务未改变」。
