# L1 实机测试报告：安装器 A08–A10、升级与地址跟随 A15

- 执行：O16 / L1，Opus，2026-11-17，分支 `go-lab-l1`（基于 `go@8489da36`）。
- 被测对象：当前 `go` 构建的 Go 面板（`server/cmd/configflow`，CGO_ENABLED=0），开启登录（ADMIN_USERNAME/ADMIN_PASSWORD/JWT_SECRET_KEY），只用合成数据，没有导入生产快照。
- Agent 产物：当前树 1.8.61-go（amd64/arm64/armv7）；上一版 1.8.60-go（`37720e95^`）；protocol-1 旧版 1.2.0-go（`0530e45b^`）。全部在测试服务器 **192.168.0.64** 上构建。
- 实验网：只用 PVE .6，从 .64 执行 `ssh pve`；只用隔离网桥 `cfgt`（10.97.0.0/24）。开工前确认 `nft inet cfgt` 的私网丢弃规则仍在。新 guest 在启动前登记到 `/root/cf-gwip-lab/l1-owner.json`。生产 guest（VM 101、VM 107、CT 105）和非本批的 CT 130 全程未碰。
- 外网：guest 经 cfgt NAT 出网，下载 apt/apk 包、GitHub 上的 mihomo/OxiDNS 核心和 Docker Hub 镜像，和以往实验相同。guest 的 DNS 设为 223.5.5.5。

## 面板放在哪里，为什么

面板放在实验网 **CT 210**（Debian 12，10.97.0.110:5001，另开 Edge 端口 8088），没有放在测试服务器上。原因是 `inet cfgt` 会丢弃实验网发往 192.168.0.0/16 的流量，guest 访问不到测试服务器；如果为此开放规则，就破坏了隔离。面板在 CT 210 里，所有 Agent 流量都留在 cfgt 内；测试服务器只通过 `ssh pve` → `pct exec` 驱动。同一台 CT 上还跑了 dnsmasq：只对 CT 214 的 MAC 发 DHCP（`dhcp-ignore=tag:!known`，`port=0` 不提供 DNS）。

- systemd 单元里不写这些值，没有中文。
- 结论：**dash 0.5.12 在 C locale 下没有把中文弄乱，也没有写坏配置，不构成缺陷。** 别人报告的问题出在 dash 0.5.13.4，比 Debian 12/13 自带的版本新，不在本批范围；如需确认，应在带 0.5.13 的系统上复测。

## 缺陷

除 D8 外都是 **Python 时代就有的问题**：Go 生成的脚本和 compose 与 Python 逐字节相同，Agent 也是同一份代码。所以它们不是重写引入的回归，但真实用户会遇到。本批没有修改代码：能修的几项都会改变「与 Python 逐字节一致」的验收基线，或者属于 Agent，不是小改动，交给协调者分派。

| ID | 严重程度 | 摘要 | 建议负责模块 |
|---|---|---|---|
| D1 | 中 | compose_compact 的数据目录含 `:` 时，`docker compose up` 必然失败 | A10（`installer/docker_ha_compact.go`、`docker_ha_guide.go` 的 `guidePath`） |
| D2 | 中 | `service_manager=command`（自定义生命周期）的 Shell 安装完成后，Agent 启动即退出 | Agent `backend/agents/go-agent/upgrade/bootstrap.go` / `migration.go` |
| D3 | 中 | 覆盖已有 Agent 的安装失败时不恢复旧 Agent；提示有误导，而且服务会一直用新配置重试 | A08（`installer/scripts/install-go.sh`，AIO 同理） |
| D4 | 低 | 设置 `AGENT_REGISTRATION_KEY` 后，所有 Shell 和普通 Docker 安装都注册不上 | A03 注册 + A08 安装器 + 文档 |
| D5 | 低 | HA 安装脚本不检查 :53，OxiDNS 已 FATAL 时仍报成功 | A09 |
| D6 | 低 | HA 验证命令用 `nslookup`，最小 Debian 12 和 Alpine 上没有这个命令 | A09 |
| D7 | 低 | 下载接口遇到超出长度的 Range 返回 500，应为 416（有意保留了 Python 的 bug） | A10 `api/agents/downloads_range.go`，需协调者决定 |
| D8 | 低 | 安装链接 404/503 由纯文本变成 JSON 包装，行为变更表没有记录这一类 | httpx（0313e086）+ `behaviour-changes.md` |
| D9 | 低（文案） | MosDNS Agent 的服务校验写成「OxiDNS 服务目录校验完成」 | Agent |

**D1 复现：** VM 213（Docker 29.10，Compose v5.7.2）上调用 HA 向导，参数 `install_method=compose_compact`、`network_mode=host`、`data_dir=/srv/cf:compact`。生成成功（Python 也对 compact 放行 `:`），但 `docker compose up -d` 报 `invalid volume specification: '/srv/cf:compact/agent:/opt/configflow-agent:ro'`。根因：compact 对含 `:` 的目录改用长格式并设 `create_host_path: true`，而 Compose 遇到 `create_host_path: true` 会退回旧的 `Binds` 字符串格式（`源:目标:ro`），路径里的 `:` 把它拆坏了。用最小 compose 验证过：同一路径设 `create_host_path: false` 可以启动，设 `true` 必然失败，这是 Docker 的格式限制，与 Compose 版本无关。compact 没有 prepare 步骤，没法预先建目录。建议：compact 和其他方式一样拒绝 `:`（`guidePath(..., false)`，提示「不能包含逗号、冒号或换行」），删掉 compact 里的 `:` 分支，在 A10 的 4 份录制语料（约 190 条含 `:` 的 compact 用例）和在线差分测试里记为有意差异，并写入行为变更表。

**D2 复现：** Debian 12，`type=mosdns`、`service_manager=command`，填写 start/stop/status/restart 命令后安装。安装器在「安装并启动 Agent 服务」失败，`journalctl -u configflow-agent` 显示 `Agent migration: migration failed; legacy executable backup unavailable: online migration supports systemd and OpenRC`。原因：`EnsureInstalled` 判定新安装还没完成迁移，于是走 `InferLifecycle`，而它只接受 systemd/openrc。可是前端和安装器都把 `service_manager=command` 作为正式选项提供（`usesCustomLifecycle`）。只要用了自定义生命周期，就一定装不上。建议：新安装由安装器直接写入「迁移已完成」标记；或者 `InferLifecycle` 对 `command` 生命周期跳过服务管理器迁移。

**D3 复现：** Alpine 上已有 OxiDNS Agent（alp-oxidns）。在注册会被拒的条件下（这里用的是 D4 的锁定），用另一个名称（alp-up）的 OxiDNS 链接安装。脚本先 `mv` 替换 `/usr/local/bin/configflow-agent` 和 `config-oxidns.json`，再启动；新 Agent 起不来，清理逻辑提示「安装未完成，正在重新启动原先运行的 Agent」，但旧程序和旧配置已经被覆盖。OpenRC 的 `respawn_max=0`（systemd 的 `Restart=always` 同理）会让新配置一直重试；锁定解除后它以 alp-up 新注册，alp-oxidns 的身份丢失，面板上留下一条孤儿记录。建议：在 `mv` 之前备份旧程序和旧配置，`RESTART_PREVIOUS_AGENT=1` 时先恢复再启动；或者至少在失败时 `disable`/`stop` 新服务，并修正提示。改动会改变生成器指纹和 A08 的逐字节基线，需要同步调整 deltas。

**D4 复现：** 面板设 `AGENT_REGISTRATION_KEY` 后，任何 Shell 安装都会出现 `Register request failed with status code: 403: Invalid registration key`。安装器和 Agent 的代码里都找不到 `registration_key`，只有 HA enrollment（installation_profile）能绕过。建议：要么由安装链接携带密钥，要么在文档里写明「锁定时只能用 HA enrollment」。

**D5 复现：** CT 215 上有一个 host 网络的 Mihomo 容器占用 :53，此时执行 HA host 安装脚本：脚本输出「本次安装的容器已启动或恢复」，退出码 0；OxiDNS 连续退出后进入 supervisor 的 FATAL 状态。预检（H2）会报 fail，但安装脚本自己不检查。建议：host 模式在启动前检查 :53，或者启动后等待 OxiDNS 进入 RUNNING 再报成功。

**D6 复现：** `action=verify` 生成的是 `nslookup example.com <VIP>`；Debian 12 云镜像没有这个命令，退出码 127。建议：加上 `dig`/`busybox nslookup` 的回退，或者提示先安装 `dnsutils`/`bind-tools`。

**D7 复现：** `curl -H 'Range: bytes=99999999-' http://<面板>/api/agents/download/configflow-agent-linux-amd64` 返回 500 `{"message":"416 Requested Range Not Satisfiable…"}`，并记一条 ERROR 日志。`downloads_range.go` 的注释说明这是有意复现 Flask 在 `except Exception` 里把 416 变成 500 的行为。按 PORTING「Python 的 bug 在 Go 里修掉」的原则，应返回 416；影响很小，由协调者决定。

**D8：** 0313e086 让所有 `/api` 错误都返回 JSON 包装。过期或不存在的安装链接现在返回 `Content-Type: application/json`，同时还带着 `Content-Disposition: attachment; filename="configflow-install.sh"`。UI 给出的命令（`curl -fsSL … -o` 或 wget）看不出区别；旧式的 `curl … | sh` 会把 JSON 当作 shell 执行，不过用户仍能在报错里看到中文提示。`behaviour-changes.md` 的 Step B #3 只写了「Werkzeug HTML 错误页 → JSON」，没有覆盖这种本来就是 `text/plain`、面向 shell 的错误。建议：补一行；或者对 `download_install_command` 的 404/503 保留纯文本。

**D9：** MosDNS 的 `-validate-service` 输出「核心服务配置检查通过：OxiDNS 服务目录校验完成」，Agent 侧的文案写错了。

## 观察（不算缺陷，留给后续批次）

- O1：macvlan HA 容器在首次心跳后 1–10 秒内，Agent 会记一条 `Returning error response: 409`（bundle、compose_direct、compact 都出现过），之后心跳和状态都正常。请求方没查到（可能是容器内的 HA companion），交给 L3 在 HA 配对时一并看。
- O2：protocol-1 更新成功后，最终事件的消息为空，与 Python `_save` 的行为一致。
- O3：同一台宿主、同一网段上只能有一个 macvlan HA 项目（Docker 拒绝重叠的地址池）。HA 本来就是每台宿主一个实例，但向导没有提示。
- O4：普通 Docker compose（bridge/host）在开着 systemd-resolved stub 的宿主机上，绑定 :53 会失败；只有 HA 向导有预检。和 Python 相同。
- O5：带 `prepare_dns_ha` 的 OxiDNS 链接没有菜单，所以没有「卸载」选项，重跑一定会重装。
- O6：修改地址接口会对公网地址（例如 8.8.8.8）发起连接尝试，然后返回 502。和 Python 的 `usable()` 一致。
