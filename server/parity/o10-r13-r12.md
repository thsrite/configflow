# O10 R13（堆外内存）与 R12（GC/内存策略）（2026-11-23）

分支 `go-perf-r13`（基于 go `3c64f4bb6`）。测量全部在测试服务器 .64/.32 上用 o10perf 跑生产快照（20261116）的私有副本，
断网命名空间，`GODEBUG=disablethp=1`（生产内核没有 THP，见 `o10-rootcause.md` 裁定 3）。

## 结论（先看这里）

1. **“约 57 MB 堆外内存”里将近一半是二进制的文件页，不是匿名内存。** 当前 go 在空闲结束、强制 GC 后 RSS 为 58–61 MB，
   其中 RssFile 25–26 MB 是可执行文件的 text/rodata（干净页，可共享，内核内存紧张时可以直接丢弃）；
   匿名内存只有 35–37 MB，由三部分组成：Go 堆映射 18 MB（存活对象只有 6.4 MB）、SQLite（modernc libc 分配器）8.4 MB、
   Go 运行时元数据 4.6 MB，再加栈约 2–3 MB。`o10-rootcause.md` §4 的 57 MB 是 RSS 减去 Go 的堆内存得到的，
   当时 run.sh 用默认 `go build`（服务器有 gcc，cgo 默认开启），带 net/http/pprof，并且在 THP 打开的机器上测量。
2. **前端资源没有嵌入二进制**（镜像从 `/usr/share/configflow/html` 用文件系统提供）。`go:embed` 一共约 0.6 MB
   （公共后缀表 238 KB、安装脚本 190 KB、OxiDNS schema 82 KB、MCP catalog 58 KB、配置模板 40 KB 等），
   只在用到时才缺页载入。这部分没有可省的空间。
3. **已改（1 个小提交）：公共后缀表合成一棵 trie。** 原来带/不带私有段的两棵 trie 合成一棵，并且叶子不再分配空 map，
   常驻内存从 1581 KB 降到 586 KB。它在第一次处理订阅主机名后一直存活。负载后存活堆 26.1→25.4 MB（.64），
   交错重测 26.0–26.3→25.1–25.3 MB（.32），延迟和 CPU 没有回退。
4. **剩下的可省项都不是“小改就能省”，列给协调者裁定**（§3）：
   (a) rankings 库维护让 SQLite 常驻多 4.7 MB；可以给 rankings 连接降低 `cache_size`，预计省 1.5–3 MB，
   但需要先测 OxiDNS 排行页的查询延迟；
   (b) **负载后存活堆比空闲多 19 MB（6.4→25–26 MB），这是负载后 RSS 的主因**，增量来自各种派生缓存和快照。
   根因报告建议派生缓存总量 ≤ 10 MB，现在已超出，建议另开一个“缓存预算”任务逐项核对；
   (c) OxiDNS schema 目录在 init 里预加载（启动时分配 3 MB、8 ms）。这是有意的快速失败设计，而且空闲循环本来就会用到，所以不改。
5. **R12 建议：保持现状，即 GOGC=100、不设固定 GOMEMLIMIT；有 cgroup 内存上限时继续用其 0.8 倍作软上限**
   （`cmd/configflow/main.go` 的 `tuneMemory`）。理由：
   - 空闲 RSS 不受 GC 参数影响。存活 6 MB、堆目标 13 MB，RSS 主要由约 40 MB 的非堆部分决定。四种设置下，空闲结束 RSS 都在 60–63 MB（.64/.32）。
   - 收紧参数只能省负载后的 10–15 MB，代价是延迟或风险：
     GOGC=50 时每请求 CPU 增加 30–70%，路由中位延迟总和增加 0–70%（取决于对照轮的机器负载），空闲 GC 次数是原来的 2.2–2.5 倍；
     GOMEMLIMIT=64MiB 在本快照上没有测出延迟代价，但它是固定值，数据量更大的用户存活堆接近 64 MiB 时，
     GC 会被限流器拉到 50% CPU（抖动）。
   - 两项 RSS 都已经明显低于 Python。空闲 60 MB 对 Python 117–123 MB，负载后静置 98–110 MB 对 Python 141–149 MB。
     不需要为了数字牺牲延迟。
   - 负载后 RSS 慢慢回落不是 scavenger 的问题。静置后 heap/free 只剩 11–12 MB，其余是存活 25 MB × GOGC 留出的堆目标，
     scavenger 按设计行事。真正要压的是第 4(b) 项的存活缓存。

## 1. RSS 分解（当前 go，.64，lean 构建，空闲 10 min）

构建：与 Dockerfile 相同（`CGO_ENABLED=0 -trimpath -ldflags='-s -w'`），用 `O10_LEAN=1` 去掉 net/http/pprof，
所以运行时 `MemProfileRate=0`，与产品一致。数据取自 `/proc/<pid>/smaps` 逐映射分类，Go 1.27 会给自己的匿名映射命名
（`[anon: Go: heap]` 等），并与 runtime/metrics 交叉核对。单位 MB。

| 类别 | 空闲结束（GC 后） | 负载后静置 5 min | 说明 |
|---|---:|---:|---|
| **总 RSS** | **58.6** | **98.0** | |
| 二进制 text（r-x） | 13.0 | 14.9 | 映射 16.3 MB；文件页，主要来自缺页预读（fault-around） |
| 二进制 rodata（含 pclntab、类型） | 11.9 | 13.2 | 映射 14.7 MB；文件页 |
| 二进制 data | 0.7 | 0.7 | |
| 二进制 bss | 2.0 | 2.0 | 映射 32 MB，绝大部分是 `crypto/internal/fips140/drbg.memory`（32 MB，未触及）；测试机 THP 占一个 2 MB 大页，生产无 THP 时约 0.2 |
| Go 堆（`[anon: Go: heap]`） | 17.9 | 53.0 | 存活对象 6.4→26.1；span 内空洞 7.7→12.8；未归还空闲页 3.7→12.3；栈 2.2→2.4 |
| Go 运行时元数据（immortal metadata、gc bits、span queue） | 4.6 | 5.6 | 随堆保留规模变化，不能单独调 |
| 未命名匿名映射 = SQLite 堆（modernc libc 分配器） | 8.4 | 8.4 | 分配器映射 11.4 MB；启动后就到达，负载不变（见下） |
| 匿名合计（RssAnon） | 35 | 72–78 | |
| 文件页合计（RssFile） | 25–26 | 28–29 | |

- `MemProfileRate=0`（与产品一致），但 runtime/metrics 仍报告 `profiling/buckets` 1.4 MB，始终不变；smaps 里没有对应的单独大映射，未进一步归因（≤ 1.4 MB）。
- **SQLite 8.4 MB 的来源**（.32，空闲 2 min，同一快照删掉某些库后对比）：完整快照为 8.6 MB 常驻 / 11.4 MB 映射；
  去掉 `metrics/oxidns_rankings.sqlite3`（76 MB）后为 3.9 / 5.0；再去掉整个 `metrics/` 仍为 3.9 / 5.0。
  所以有 4.7 MB 来自 rankings 库的每小时维护：`MaintainContext` 对 76 MB 库做 DISTINCT 和合并，
  页缓存默认 2000 KiB，还有临时 B 树。modernc 的分配器会保留释放的区域，每个尺寸类最多保留 4 MB 不交还给系统
  （`modernc.org/memory` 的 `hotBytes`），libc 不暴露 Trim，所以这部分会一直驻留。
  其余 3.9 MB 是主库的 2 个常驻读连接（R10）、连接级结构和分配器的保底保留。
  modernc 构建关闭了 `sqlite3_memory_used` 统计（返回 0），只能看分配器映射量。
- **全局初始化**（`GODEBUG=inittrace=1`）：所有包的 init 共分配 7.06 MB、6 万次。最大的是 `internal/oxidns`
  （3.0 MB / 26.6k 次 / 8.2 ms，预加载 schema 目录）、`agents/monitor` 0.84 MB、`installer` 0.37 MB、`auth` 0.29 MB；
  其余每项 ≤ 0.25 MB。空闲存活堆一共只有 6.4 MB，延迟加载最多能省 1–2 MB 的存活量，
  而且 OxiDNS 目录在空闲的 discovery 轮次里本来就会用到。
- **二进制组成**（`go tool nm -size`）：text 16.8 MB，其中 configflow 自身约 9.3 MB、modernc sqlite/libc 2.0 MB、crypto 0.9 MB、net 0.65 MB；
  data 段最大的是 x/text 的 CJK 编码表（约 0.6 MB，只在用到时缺页）。text/rodata 是文件页，缩小二进制收益不大，不建议为此动结构。

## 4. R12：GC 设置对比

均为当前 go（R13 改动之后），lean 构建，THP 关。“负载后”指负载结束后静置 60 s/300 s 的 RSS；CPU/次和延迟是 19 条路由的合计。

### 4.1 .32/.64 各跑两种设置（空闲 10 min + 负载 10 次 + 静置 300 s）

| 设置（主机） | 空闲 CPU | 空闲 GC 次数 | 空闲 RSS 结束（匿名） | 负载后静置 300 s RSS | 负载后存活 / 堆目标 | 路由 CPU 合计 |
|---|---:|---:|---:|---:|---:|---:|
| GOGC=100（.32） | 1.06%¹ | 154 | 61（37） | 100 | 26.4 / 56.2 | 407 ms |
| GOGC=50（.32） | 1.07%¹ | 388 | 60（34） | 90 | 25.9 / 39.4 | 576 ms（+41%） |
| GOMEMLIMIT=96MiB（.64） | 0.84% | 155 | 63（37） | 105 | 26.1 / 52.6 | 421 ms |
| GOMEMLIMIT=64MiB（.64） | 0.58% | 181 | 62（36） | 94 | 26.4 / 39.4 | 454 ms（+8%） |

¹ .32 当时 loadavg 9–12，空闲 CPU 只能作参考。96 MiB 上限在本快照上不起作用（Go 自身内存 < 96 MiB），等同于基线。

### 4.2 交错重测（.32，同一台机器，8 轮依次运行，空闲 1 min + 负载 20 次 + 静置 60 s）

| 轮次（开始时 loadavg） | 路由延迟合计 | CPU/次合计 | mihomo+provider 中位 | 负载后静置 RSS | 负载后存活 / 堆目标 |
|---|---:|---:|---:|---:|---:|
| R13 前 GOGC=100（7.7） | 404 ms | 470 ms | 229 ms | 107–108 | 26.3 / 53.9 |
| R13 后 GOGC=100（6.3） | 330 ms | 395 ms | 188 ms | 104–110 | 25.1 / 51.3 |
| R13 后 GOGC=50（3.8） | 572 ms | 686 ms | 293 ms | 91 | 25.1 / 38.4 |
| R13 后 GOMEMLIMIT=64MiB（10.0） | 393 ms | 435 ms | 221 ms | 95–98 | 25.1 / 42.5 |
| R13 后 GOGC=100（34.8） | 526 ms | 523 ms | 291 ms | 111–116 | 25.3 / 52.2 |
| R13 前 GOGC=100（18.6） | 545 ms | 565 ms | 259 ms | 107–109 | 26.0 / 52.9 |
| R13 后 GOMEMLIMIT=64MiB（21.8） | 323 ms | 419 ms | 180 ms | 95 | 24.9 / 39.8 |
| R13 后 GOGC=50（4.3） | 532 ms | 684 ms | 277 ms | 91 | 25.1 / 38.3 |

读法：GOGC=50 即使在机器最空闲时（loadavg 3.8–4.3）也是 CPU 最高的两轮，每请求 CPU 比 GOGC=100 多 30–70%，
这是真实代价。GOMEMLIMIT=64MiB 与 GOGC=100 的差异落在机器负载造成的噪声内，负载后 RSS 稳定少 10–15 MB。
各设置下空闲 RSS 都在 49–54 MB（1 min 空闲），没有区别。

### 4.3 建议值与理由

- **默认：GOGC=100，不设 GOMEMLIMIT；有 cgroup 上限时软上限取 0.8 倍（现状，不改代码）。**
  对固定值 64 MiB 的担心：本快照负载后存活 25 MB，留出的余量够；但存活堆与 Agent 数量、历史长度、订阅/规则缓存同比增长，
  对数据量大一倍的用户，64 MiB 会让 GC 频繁运行、被限流器拉到 50% CPU，这正是“为数字牺牲延迟”。
  cgroup 比例上限只在接近 OOM 时才收紧，没有这个问题。
- 小内存主机（例如容器只给 128 MB）已经自动得到 102 MB 软上限，不需要另设。
- 不建议定期 `debug.FreeOSMemory()`：静置后可回收的空闲页只有 11–12 MB，下一次分配高峰会重新长回来，还要多付一次强制 GC 和全量 scavenge。
- 如果以后要降负载后 RSS，应该做 §3-B（压存活缓存）：存活每少 1 MB，GOGC=100 下 RSS 约少 2 MB，而且没有 CPU 代价。

## 复现

```bash
# 分解（产品同款构建，堆采样关闭）
RT_HOST=sunbroke@192.168.0.64 rt -e GODEBUG=disablethp=1 -e O10_LEAN=1 -- server/tools/o10perf/run.sh \
  --servers go --idle-minutes 10 --iterations 10 --mem-detail --settle-seconds 300
# 加 SQLite 分配器映射量：再加 -e O10_TAGS=memory.counters
# GC 设置：再加 -e GOGC=50 或 -e GOMEMLIMIT=64MiB
# 全局初始化分配：GODEBUG=inittrace=1 DATA_DIR=$(mktemp -d) ./configflow --check
```
