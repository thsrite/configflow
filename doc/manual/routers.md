# 上游路由

这里的“上游路由”通常就是家里的主路由器。ConfigFlow 可以连接 iKuai 4.x 或 RouterOS 7.1+，把需要分流的连接交给 Mihomo，并让设备使用 OxiDNS。

**保存接入资料不等于修改路由器。** 正常流程是添加 → 探测 → 差异报告 → 预览发布 → 确认发布。实际写入前，请看清目的地址、代理设备和 DNS 地址。

## 添加路由器：每个字段怎么填

| 字段 | 填什么 / 默认值 | 推荐与效果 |
| --- | --- | --- |
| 名称 | 自己能辨认的名字，如“家里主路由” | 只用于识别 |
| 类型 | iKuai 4.x 或 RouterOS 7.1+ | 必须与实际系统一致，不能选择普通家用路由器代替 |
| 管理地址 | 完整地址，如 `https://192.168.1.1` | 填主路由后台地址，不是 Mihomo 的代理端口 |
| 用户名、密码 | 能使用相关管理接口的账号 | 编辑时密码留空表示保留旧密码；请先确认面板所在设备能访问路由器 |
| 校验 HTTPS 证书 | 默认开 | 有可信证书时保留；自己的路由器使用自签证书且确认地址正确时可关，否则证书验证失败会阻止连接。HTTP 下此开关不起作用 |
| 代理网关（Mihomo Agent） | 默认不关联 | 选实际接收主路由转发连接的 Mihomo。只保存关联不会自动让它具备转发能力 |
| DHCP DNS 服务器（OxiDNS Agent） | 默认不关联 | 选设备应使用的 OxiDNS；RouterOS 同时核对该 LAN 的 IPv6 DNS 下发。不关联则保留现有设置。关联 HA 成员时页面会提示实际使用 VIP |

RouterOS 的 HTTPS 管理服务需要 `www-ssl`；使用 HTTP 的 `www` 需要 RouterOS 7.9+。iKuai 4.x 通常把 HTTP 转到 HTTPS，出厂自签证书可能需要关闭上述校验。ConfigFlow 不会替路由器升级系统或打开管理服务。

首次使用向导中，安装完成后会自动关联那次安装的 Mihomo 和 OxiDNS，因此表单可能不显示手动选择框。

## 决定哪些连接交给 Mihomo

| 选项 | 默认 / 推荐 | 打开或选择后的结果 | 关闭或不选的结果 |
| --- | --- | --- | --- |
| 自动配置回流 | 默认关；只有网络确实要求回复先回主路由时才开 | 维护让 Mihomo 的回复经过主路由返回设备的规则；iKuai 会改用排除 Mihomo 自身的端口分流 | 普通静态路由方式；取消后需发布才清理本功能写入且不再被其他路由器使用的回流规则 |
| 使用静态路由的 IP 规则集 | 默认不额外选 | 所选清单中的 IPv4 目标地址交给 Mihomo，不限定某一台来源设备；RouterOS 在 Mihomo 使用 IPv6 时，其中的公网 IPv6 网段也交给 Mihomo，见下文 | 仍自动包含 fake-ip 网段；不是完全关闭分流 |
| 使用策略路由的 IP 规则集（RouterOS） | 默认不选 | 只有指定的智能分流设备访问这些 IPv4 目标时才交给 Mihomo | 不建立这类按设备选择的目标规则；fake-ip 仍走静态路由 |

fake-ip 是 OxiDNS/Mihomo 用于分流的临时地址。已经通过这种方式分流的网站，不必再把它的所有真实 IP 手工加入静态路由。Telegram 等可能直接连接 IP 的应用，才需要另外考虑对应 IP 规则集。

需要自己登录路由器逐条填写时，见 [Fake-IP 与 Telegram 静态路由填写表](../guide/first-run.md#manual-routes)，其中列出了目的网段、子网掩码和下一跳。**下一跳填运行 Mihomo、负责接收转发连接的设备 IP**；真实 IP 规则还需按来源排除 Mihomo 设备本身。

静态规则集和策略规则集不能同时选同一项，移到一组会从另一组移除。取消勾选后必须**保存、预览并确认发布**，才会清理对应受管规则；单纯关掉窗口不会修改路由器。

### IPv4 同口转发的防火墙提示（RouterOS）

主路由把 fake-ip 网段和规则集 IPv4 网段交给同一 LAN 上的 Mihomo 时，设备的连接先到 ROS，再从同一个 LAN 口转给 Mihomo；Mihomo 的回包直接发给设备，不经过 ROS。ROS 只看到连接的第一个包，之后的包被判为 `invalid`。RouterOS 出厂 IPv4 防火墙的 forward 链有 `defconf: drop invalid`，会丢弃这些包：新连接可能卡几秒甚至超时（实验网 RouterOS 7.25 实测每次约 6.6 秒，有时 13 秒；2026-10-31 复测 10 个新连接都超过 5 秒客户端超时），长连接也会卡一次。

ROS 会给设备发 ICMP 重定向，让设备改为直接连 Mihomo，但每个设备只发几个、随后暂停约 20 秒，同时打开多个新地址时大部分仍会卡；开启了转发的 Linux 设备还会忽略重定向。重定向只能部分缓解，不能依赖；关闭 `send-redirects`、FastTrack 都不能解决。所以只要 forward 链会丢弃「从 LAN 口进、又从同一口出、状态为 invalid」的包，差异报告就在「代理路由」表格下方提示，并给出一条可复制的命令，例如：

```
/ip firewall filter add chain=forward action=accept in-interface=bridge out-interface=bridge comment="LAN to Mihomo via router" place-before=*7
```

执行后，同口转发的连接恢复到毫秒级。说明：

- 只检查 RouterOS，且只在这台路由器有（或本次将发布）指向 Mihomo 的 IPv4 路由时检查；开启「自动配置回流」时回包经过 ROS，不会出现这个问题，也不检查。
- `place-before` 指向 forward 链里**实际先处理这些包**的那条规则：按规则顺序模拟一个这样的包，跳过不可能匹配的规则，取第一条会处理它的规则。出厂防火墙就是 `drop invalid`；你改过注释、或在前面加了自己的丢弃规则或跳转，命令也会放在它前面。
- 读不到防火墙或确定不了 Mihomo 所在的 LAN 口时，显示「未能确认」，不当作没有问题。
- 只提示，ConfigFlow 不修改防火墙；路由照常发布，自动同步规则也不受影响。执行命令后重新生成差异报告，提示消失即可。
- IPv4 与 IPv6 是两套防火墙，IPv6 的提示和命令见下文，两条都要执行。

### IPv6 Fake-IP 分流路由（RouterOS）

和 IPv4 的 fake-ip 网段一样，只要 Mihomo 使用 IPv6（顶层 `ipv6` 为 `true`）、DNS 是 Fake-IP 模式且填写了 `fake-ip-range6`，差异报告就显示「IPv6 Fake-IP 分流路由」，把这个网段（如 `fc00::/64`）交给 Mihomo，不看 `dns.ipv6`。所以 Mihomo 设置的两个 IPv6 模式发布的是同一条路由，在两者之间切换不用再改路由器；DNS IPv6 关闭时客户端拿不到这个网段的地址，属于正常情况。

- 只有「客户端也走 IPv6」（`dns.ipv6: true`）要求 Mihomo 开启 TUN，未开启时阻止发布；另一个模式照常发布。
- 下一跳的选择和沿用已有路由与下文 IPv6 规则集路由相同；但无法唯一确定下一跳、已有路由冲突或网段与 ROS 地址重叠时，这一项会阻止整次发布，不像规则集路由那样只跳过。
- 「IPv6 模式」改为「关闭」、DNS 不再使用 Fake-IP 或删除网段后，保存并经差异报告**预览发布**，才撤回 ConfigFlow 添加的路由。
- 自动规则同步不发布这项改动：首次出现、网段或下一跳变化时暂停同步，需要手动预览发布一次。

![「Mihomo 用 IPv6，客户端走 IPv4」（DNS IPv6 关闭）时，差异报告中的 IPv6 Fake-IP 分流路由待添加](../img/guide/mihomo-ipv6-nodes-fakeip-pending.png)

### IPv6 规则集路由（RouterOS）

Telegram 等规则集里除了 IPv4 网段，还有 `IP-CIDR6` 网段。设备有 IPv6 后会直接用这些 IPv6 地址连接，如果主路由只把 IPv4 网段交给 Mihomo，这些连接会从 WAN 直连并超时。

满足以下条件时，差异报告在 Fake-IP 下方显示「IPv6 规则集路由」：

- 路由器类型是 RouterOS。iKuai 只发布 IPv4 网段，规则集中的 IPv6 网段不会处理，差异报告会提示数量。
- Mihomo 使用 IPv6：基础 YAML 顶层 `ipv6` 为 `true`，未填写时按 Mihomo 默认开启；Mihomo 设置的「IPv6 模式」选「Mihomo 用 IPv6，客户端走 IPv4 分流」或「客户端也走 IPv6」时都满足。
- Mihomo 开启了 TUN（`tun.enable: true`）。主路由转来的 IPv6 连接只能由 TUN 接收。
- 「使用静态路由的 IP 规则集」中有公网 IPv6 网段。链路本地、ULA 等非公网网段不处理；「使用策略路由的 IP 规则集」只处理 IPv4。

每个网段添加一条 `/ipv6/route`，下一跳与 IPv6 Fake-IP 的选择方式相同：优先这台 Mihomo 唯一的链路本地地址，并带上 LAN 接口（如 `fe80::1234%bridge`）；没有时才用同一 LAN 的唯一 ULA。已有路由正确指向这台 Mihomo 的继续沿用，不因优先级不同而更换。

| 状态 | 含义 |
| --- | --- |
| 待添加 | 发布时添加指向 Mihomo 的路由，并登记为 ConfigFlow 受管对象 |
| 已同步 | 受管路由已生效 |
| 待更新 | 下一跳变化需要替换，或规则集不再包含此网段、Mihomo 已关闭 IPv6，发布时撤回 |
| 沿用已有路由 | 别人建的路由已经正确指向 Mihomo，只沿用，不接管；关闭后不会删除它 |
| 冲突 | 同一网段已有指向别处、停用或多条路由，或 ROS 自身的 IPv6 地址在此网段内。这一网段跳过，不覆盖 |
| 待确认 | 受管路由未生效，或这一项本次跳过 |

**无法唯一确定下一跳时只跳过这一项，不猜测，也不阻止整次发布。** 例如 Mihomo 有多个链路本地地址且没有已在用的那个、Agent 离线或版本太旧、ROS 无法读取 IPv6、受管路由被手工修改。预览会提示「IPv6 规则集路由本次跳过」，IPv4 路由、规则和 DNS 照常发布，已有 IPv6 路由保持原样。按提示处理后重新生成差异报告。

把 Mihomo 的「IPv6 模式」改为「关闭」或取消相关规则集后，保存并经差异报告**预览发布**，才会撤回 ConfigFlow 添加的 IPv6 规则集路由；沿用的、手工添加的路由不会删除。新增和删除都分批写入，写后回读核对，失败时撤销本次改动。

**自动规则同步**：手动发布过一次后，远程规则集的 IPv6 网段增减会像 IPv4 一样自动应用，同样批量写入、回读，失败时连同本轮 IPv4 改动一起回滚并暂停同步。首次发布、Mihomo 的 IPv6 下一跳变化、关闭 IPv6、受管路由被手工删除，以及本项被跳过时，自动同步不改 IPv6 路由，只更新 IPv4，并在同步结果中说明需要手动预览发布；不会因此暂停同步。IPv6 Fake-IP 路由不在自动同步的范围内。

**防火墙提示：同口转发被「drop invalid」丢弃。** 设备经 ROS 的同一 LAN 口把连接转给 Mihomo，Mihomo 的回包直接发给设备，不经过 ROS。ROS 只看到连接的第一个包，之后的包被判为 `invalid`。RouterOS 出厂 IPv6 防火墙的 forward 链有 `defconf: drop invalid`，会丢弃这些包，新连接可能卡几秒甚至超时。下一跳是链路本地地址加接口时，RouterOS 会给设备发 ICMPv6 重定向，让设备改为直接连 Mihomo：设备逐个建立连接时基本不卡（实验网 RouterOS 7.25 实测 10 个新连接都成功，0.2–1.1 秒），但重定向有限速（约每秒 1 个），同时打开多个新地址时仍有连接卡住，长连接也会卡一次；开启了转发的 Linux 设备或忽略重定向的设备，每个新连接都会卡住（实测 6.6–7.4 秒，或超过 5 秒客户端超时）。重定向只能部分缓解，不能依赖，所以只要 forward 链有生效的 `drop invalid`、且前面没有放行 LAN 进 LAN 出，就会提示，与下一跳类型无关。提示文字与 IPv4 同口转发共用。IPv6 Fake-IP 与本项走同一路径，差异报告按 forward 链的规则顺序检查这种情况，命中时在「IPv6 Fake-IP 分流路由」或本项显示提示和一条可复制命令；两项都受影响时，命令只在「IPv6 Fake-IP 分流路由」中显示一次，本项注明见上方。例如：

```
/ipv6 firewall filter add chain=forward action=accept in-interface=bridge out-interface=bridge comment="LAN to Mihomo via router" place-before=*B
```

命令只放行从该 LAN 口进、又从同一口转出的连接，`place-before` 指向 forward 链里实际先处理这些包的规则（出厂即 `drop invalid`，规则定位方式与 IPv4 相同），同时覆盖 IPv6 Fake-IP 网段和规则集网段。防火墙由你管理，ConfigFlow 不会自动写入；路由照常发布。执行后重新生成差异报告，提示消失即可。

与 IPv4 静态路由相同，路由只看目的地址：如果 Mihomo 自己用 DIRECT 直连这些 IPv6 地址，连接会被主路由送回 Mihomo。规则集应走代理。

## DHCP DNS 和强制 DNS

关联 OxiDNS 后，发布会尝试修改能唯一确定的 IPv4 DHCP 网段，**用所选 OxiDNS 替换该网段的 DNS 列表，不保留旧备用 DNS**。设备通常要重新连接网络或续租地址才会取得新值。如果无法唯一判断网段，应先核对网络和预览，不要猜。

### IPv6 DNS 下发（RouterOS）

设备即使已通过 IPv4 DHCP 获得 OxiDNS，也可能通过 IPv6 路由器通告（RA）再收到另一套 DNS。关联 OxiDNS 后，差异报告会在「DHCP DNS」下方显示「IPv6 DNS 下发」，检查**所选 Mihomo 网关所在的同一 LAN**。

![路由器核对清单中的 IPv6 DNS 下发及待关闭说明](../img/guide/router-ipv6-dns.png)

| 检查结果 | 含义与下一步 |
| --- | --- |
| 待关闭 | 该 LAN 仍通过 RA 下发 DNS。点「预览发布」，核对 LAN 接口和改动，再确认发布 |
| 无需调整 | 该 LAN 当前没有通过 RA 下发 DNS，本次不需要改这一项；不代表已测试所有设备的 DNS 查询 |
| 需处理 | 还不能安全确定修改范围，或通告配置无法读取、存在动态或无效条目；本次发布跳过这一项，其他改动照常发布。按显示的原因处理后重新检查 |

未关联 OxiDNS 时不显示此检查项，也不读取或修改 IPv6 DNS 下发，不能据此认为路由器已经关闭它。

确认发布时，ConfigFlow **先写入并核对 IPv4 DHCP 的 OxiDNS 地址，再把已确认 LAN 的 `advertise-dns` 改为 `no`**。IPv6 地址前缀和默认网关仍照常通告，设备仍可获得 IPv6 地址并使用 IPv6 网络。检查本身不写入，也没有跳过预览的单独关闭开关。写入后会回读核对；失败时尝试回滚本次已完成的修改，需查看发布与回滚结果。

「需处理」只影响这一项：预览会提示「IPv6 DNS 下发本次跳过」，路由、规则和 DHCP DNS 照常发布，发布记录中这一项标为需处理，RA 通告保持原样。自动规则同步也不会因此暂停。

RouterOS 出厂只有一条共享的 `interface=all` 通告。DNS 通告来自它、又没有该 LAN 的专用条目时，ConfigFlow 不会直接关闭 `all`，以免连带影响其他网段或上网接口。卡片会给出一条可复制的命令，例如：

```
/ipv6 nd add interface=bridge advertise-dns=no ra-interval=3m20s-10m ra-lifetime=30m ...
```

它为该 LAN 单独建立通告条目，除 `advertise-dns=no` 外的参数照抄当前 `all` 条目；专用条目优先于 `all` 生效，`all` 和其他接口保持不变。在 RouterOS 终端执行后重新生成差异报告，这一项显示「无需调整」。该 LAN 已有停用的专用条目或存在多条通告时，不提供命令，请在 **IPv6 → ND** 中手动整理。

关闭后，设备可能仍暂时保留先前获得的 DNS，需要重新联网或等待旧 DNS 通告过期。这项操作只调整该 LAN 的 RA DNS 下发，**不修改 ROS 自身 DNS、上游连接的 `use-peer-dns` 或 DHCPv6 服务器设置**。设备手写 DNS、应用自带的加密 DNS，以及其他设备发出的 DNS 通告仍可能走别的路径；此项不等于接管全部 DNS 流量。

### 强制 DNS（RouterOS）

RouterOS 还提供以下选项：

| 开关 / 输入框 | 当前初始值 | 启用后的作用 | 推荐与未启用结果 |
| --- | --- | --- | --- |
| 强制局域网 DNS 走 OxiDNS | 关，需先选 OxiDNS | 把 IPv4 设备发往其他地址的普通 53 端口查询转给 OxiDNS；自动放行 Mihomo 和 OxiDNS 本身 | 先保持关、验证基础方案。关闭时，写死公共 DNS 的设备可能绕过 OxiDNS |
| 拦截加密 DNS（853 端口） | 关 | 拒绝 853 端口连接，促使支持回退的设备改用普通查询 | 只在需要时开。指定了私人 DNS 主机名的手机可能直接无法解析，需要把手机改成自动。它不是对所有加密 DNS 的统一拦截 |
| OxiDNS 故障时自动暂停 | 开 | 每 10 秒检查 OxiDNS 的 TCP 53，无应答时停用劫持，恢复后再启用 | 推荐保留。关闭时故障期间仍会强制转发；该开关不修改路由器自身 DNS，也不能保证所有设备都有可用备用 DNS |
| 放行设备 | 空 | 每行填一个 IPv4 地址或网段，允许它保持原 DNS | 测试机或确需例外的设备使用；不要重复填写自动放行的核心设备 |

以上强制 DNS 功能只处理这里注明的 IPv4 流量，不会替你接管 IPv6 DNS 或所有通过 HTTPS 的名称查询。

## IPv6 前缀变化保护（RouterOS）

宽带通过 PPPoE / DHCPv6 获得 IPv6 前缀（PD）时，运营商可能在重拨或路由器重启后换一个前缀。RouterOS 重启后会忘记旧前缀，不会通知设备停用它；手机、电脑继续用旧地址发起连接，IPv6 会断网，直到旧地址过期。前缀从 A 换到 B 再换回 A 时，Linux 等设备还可能一直沿用旧源地址。

在路由器设置中打开「IPv6 前缀变化保护」（仅 RouterOS，默认关闭），保存后到差异报告查看「IPv6 前缀变化保护」卡片，再经「预览发布」确认写入。它在路由器上安装三样东西：

| 对象 | 作用 |
| --- | --- |
| 脚本 `cf-pd-watch` | 记录当前 LAN 的 /64 前缀；发现前缀变化时，把旧前缀以「首选时间 0、有效 10 分钟」继续通告 1 小时（3600 秒），设备随即改用新地址。旧前缀重新变成当前前缀时撤掉弃用通告并重新通告 |
| 定时任务 `cf-pd-poll` | 开机后每 30 秒运行一次脚本，作为兜底 |
| IPv6 DHCP 客户端的钩子 | 写在请求前缀的那条 `/ipv6 dhcp-client` 的 script 字段里：拿到新前缀后每秒运行一次脚本，共 10 次，通常 1–3 秒内完成切换 |

**参数自动识别，不需要填写**：地址池取启用中、`request` 含 `prefix` 的 IPv6 DHCP 客户端的 `pool-name`（停用的出厂条目会被跳过）；LAN 取 `/ipv6 address` 中使用该地址池且启用的接口，地址池分给多个 LAN 时取 Mihomo 网关所在的 LAN，其余 LAN 会在卡片上列出、不受保护。出现多条请求前缀的客户端、没有 LAN 使用该地址池、LAN 地址不是 /64 或未开启 `advertise` 等无法唯一确定的情况时，卡片显示「需处理」和原因；**本次发布只跳过这一项，路由、规则和 DNS 等改动照常发布**。

| 卡片状态 | 含义与下一步 |
| --- | --- |
| 已安装（沿用） | 路由器上已有手动安装，规范化比较（忽略注释、空行和缩进）后脚本、定时任务、钩子都与 ConfigFlow 模板一致，参数也一致。ConfigFlow 不改写它，也不把它算作受管对象，**关闭开关时不会删除** |
| 待发布 | 需要新建、更新或撤回。表格逐项写明差异（如 LAN、地址池、弃用通告时长或模板版本不同、旧版单次运行的钩子），预览里能看到改前和改后的完整字段 |
| 已安装 | 由 ConfigFlow 安装或更新过，归 ConfigFlow 管理 |
| 需处理 | 无法确定参数，或存在冲突；本项保留现状 |

**冲突时不覆盖**：IPv6 DHCP 客户端的 script 字段已有其他内容、或已有同名但内容不同的脚本 / 定时任务时，ConfigFlow 不改写，只在卡片上提示。钩子可以手动追加到原内容末尾，卡片会给出要追加的那一行；追加后这段内容视为共用，撤回时保留。

**关闭与撤回**：关闭开关并预览发布后，ConfigFlow 只撤回自己安装或更新过的对象（脚本、定时任务、钩子），并清除脚本留下的 `cf-pd-last` 地址记录和弃用前缀通告。「沿用」的手动安装不在撤回范围内；如果确认发布时更新过手动安装，更新后它归 ConfigFlow 管理，关闭开关时一并撤回。手动安装留下的卸载脚本 `cf-pd-rollback` 不会被使用或删除。路由器上的这些对象被手动改成其他内容时，撤回会停止并提示核对。

所有写入通过 RouterOS REST 接口完成，发布前重新读取确认与预览一致，写后回读核对，失败时撤销本次已完成的修改。自动规则同步不会发布这一项，出现差异时会暂停并提示手动预览。

## 表格里的按钮

| 按钮 | 做什么 | 是否影响真实设备 |
| --- | --- | --- |
| 探测 / 检查连接 | 检查地址、账号和接口，显示版本与结果 | 不发布网络设置 |
| 差异报告 / 查看改动 | 比较现有状态与期望状态 | 只检查 |
| 预览发布 | 列出将新增、修改或删除的内容 | 尚未执行发布 |
| 确认发布 | 按预览写入并回读检查 | 会；失败会尝试撤销本次改动，必须查看发布和回滚结果 |
| 编辑 | 修改 ConfigFlow 中的接入资料和目标设置 | 保存后仍需发布 |
| 删除 | 移除 ConfigFlow 的接入记录 | 不删除路由器上的既有设置；不是撤销发布按钮 |
| 静态路由 | 查看并手动管理具体路由 | 每次新增、修改、删除先预览，确认后才写入 |
| 策略路由 | 管理 RouterOS 按设备与目标地址分流 | 见下节 |
| 规则同步 | 安排已发布 IP 清单的自动更新 | 开启后会按计划写入变化 |

差异报告中的“NAT 免转换”是让被转交的连接保留必要信息的处理；“回流规则”是让回复走正确返回路径的处理。阅读每项展开详情，确认 IP、网关及增删数量，而不是只看到绿色状态就发布。

发布失败后不要连续重复点确认。若显示回滚未完成或结果待确认，先阅读具体失败项、核对路由器当前状态，再决定重试。

## 待发布提醒与直达链接

保存 Mihomo 设置后，不必自己回到这里找差异。设置窗口底部的发布栏（生成页、Agent 设置和 Mihomo 面板相同）在保存草稿或保存并发布后，会实时读取**正在编辑的配置空间内**把这台 Mihomo 设为代理网关的路由器，逐台提示；IPv6「检查设备」窗口每次检查后也会显示：

| 提示 | 含义 | 按钮 |
| --- | --- | --- |
| 不显示 | 差异报告和发布预览都没有需要写入的内容 | — |
| 上游路由「名称」有 N 项待发布 | N 是「预览发布」中各阶段的改动数之和；检查窗口另列出如「IPv6 Fake-IP 分流路由：待添加」 | 查看并发布 |
| 上游路由「名称」有改动暂时无法发布 | 预览中有阻止发布的问题，或某项只能跳过，原因直接显示 | 查看原因 |
| 无法确认上游路由「名称」状态 | 读取路由器失败或超过 25 秒，不当作已同步 | 查看差异报告 |

提示只读取，不修改路由器。路由器记录、配置空间修订号和 Agent 记录都没变时，同一台 Mihomo 一直沿用上次读取，并注明「检查于 N 分钟前」；保存、发布成功或点「重新检查」后重新读取，读取失败的结果不沿用。在路由器上直接做的修改不会自动发现，需要点「重新检查」。其他空间中即使有同名、同 ID 或关联同一 Mihomo 的路由器，也不会计入本窗口的待处理数量或出现在链接中。因此在 Default 的 Mihomo 设置中点「查看原因」，目标仍是 Default 内的路由器。

按钮打开 `/routers?router=<路由器>&profile=<配置空间>&preview=1`：进入本页后直接生成这台路由器的差异报告，并打开「预览发布」窗口。看完改动后点「确认发布」才会写入，点「取消」不修改任何内容。路由器属于其他配置空间时，页面先切换到该空间并提示；空间已删除或当前配置正在保存时只提示原因，不打开预览。不带 `preview=1` 时只打开差异报告。

## 手动管理静态路由

“刷新路由”读取当前列表。“新增路由”填写目的网段、下一跳和可选备注：

- **目的网段**是要送去处理的地址范围，例如 `192.168.50.0/24`。
- **下一跳**是负责接手的设备 IPv4，不是随意挑选一个同网段地址。
- **启用路由**新增时默认打开，确认写入后该条路由才参与转发；关闭后确认写入会保存为停用状态。

点“预览路由变更”，核对后确认写入。删除也要先预览并确认。界面不允许编辑的系统条目不能强改；带 `cf` 标记的受管路由之后可能被自动发布调整。这里的手工操作不会同时调整 NAT、DHCP DNS 或 Mihomo 回流配置。

## RouterOS 按设备分流

1. 到 [客户端设备](client-devices.md)，把需要参与的 IPv4 设备或网段设为“智能分流”。更具体的直连例外和 Mihomo 自身会排除。
2. 回到“策略路由”，检查来源设备，选择代理网关和目标 IP 规则集。需要时点“编辑规则内容”。
3. 在“OxiDNS 发布目标”核对需要同步的设备，首次加载默认勾选页面列出的全部来源 OxiDNS。勾选会发布该空间完整已保存配置，包含其他草稿；全部取消则只发布 RouterOS。
4. 点“保存并预览”，核对改动。预览后再改发布目标会使预览失效，需要重新点“保存并预览”。
5. 点“确认发布”。选了 OxiDNS 时先逐台发布 OxiDNS，再发布 RouterOS；中途失败或结果未确认时暂停后续步骤。

“重新载入”用于重新读取保存状态；有未保存修改时先处理提示。“核对发布结果”用于结果未确认时查询实际进度，不是重新发一遍。已经成功的设备保留成功结果，不能假设任一步失败就把所有设备同时退回。

## 自动同步规则到 ROS

默认关闭，检查频率默认每小时，可选 15 分钟到 24 小时。先成功发布一次建立基准，再开启。

开启后只追踪**已选中并成功发布过的远程规则集中的 IPv4 变化**：静态组更新路由，策略组更新目标地址列表。不会把域名自动转换成 IP，也不会接管无登记的手工路由。

| 按钮 / 状态 | 怎么处理 |
| --- | --- |
| 自动同步规则到 ROS | 开启后定期写入 IP 增删；关闭只停止后续检查，不删除已发布规则 |
| 检查频率 | 普通使用先保留每小时，不必频繁刷新 |
| 刷新状态 | 查看最新任务结果，不触发一次规则同步 |
| 立即同步 | 满足条件后提前执行一次；不是首次发布的替代 |
| 已暂停，需核对 | 格式异常、原来可用 IP 全消失等情况会保留旧规则；修复后重新预览并确认发布，建立新基准 |

修改来源设备、网关、规则集选择或其他路由设置后，仍要手动预览发布。这里的自动同步只负责 RouterOS，Mihomo 和 OxiDNS 仍按各自的更新流程工作。
