# Mihomo IPv6 检查与准备

Mihomo 设置里的「IPv6 模式」按使用场景三选一，下方列出这个模式还需要完成的步骤。

| IPv6 模式 | 适合 | YAML |
| --- | --- | --- |
| 关闭 | 不使用 IPv6 | 顶层 `ipv6: false`，`dns.ipv6` 同为 `false` |
| Mihomo 用 IPv6，客户端走 IPv4 分流 | 只让 Mihomo 经 IPv6 连接节点，客户端继续按 IPv4 分流 | `ipv6: true`，`dns.ipv6: false`；Fake-IP 模式下补齐 `fake-ip-range6` |
| 客户端也走 IPv6 | 手机、电脑也拿到 IPv6 地址，经 Mihomo 分流 | `ipv6: true`，`dns.ipv6: true`；Fake-IP 模式下补齐 `fake-ip-range6` |

界面上第二个模式的选项名是「Mihomo 用 IPv6，客户端走 IPv4」，选中后的说明写出完整名称。

**IPv6 Fake-IP 路由和 IPv4 一样默认发布。** 只要 Mihomo 使用 IPv6（顶层 `ipv6` 为 `true`）、DNS 是 Fake-IP 模式且填写了 `fake-ip-range6`，上游路由就把这个网段（如 `fc00::/64`）路由到 Mihomo，不看 `dns.ipv6`。两个 IPv6 模式发布的是同一条路由，之后在两者之间切换不用再改路由器；选择「关闭」后经预览发布撤回。

「Mihomo 用 IPv6，客户端走 IPv4 分流」需要在 Mihomo 主机上补齐 IPv6 转发、`accept_ra` 等设置，再发布 Mihomo。DNS 只给客户端返回 IPv4 地址，客户端暂时用不到已发布的 IPv6 Fake-IP 网段，这是正常情况，检查不会报错。客户端有 IPv6 时，规则集里的公网 IPv6 网段也会发布到上游路由，见下文「IPv6 规则集路由」。

「客户端也走 IPv6」时客户端会拿到 IPv6 Fake-IP 地址，因此 Mihomo 必须开启 TUN 接收这些连接，未开启时检查报错、路由暂不发布；另一个模式只记一句提示。forward 链有生效的「drop invalid」时，要在它前面放行 LAN 进 LAN 出的连接（两个模式都适用）；NAT 不能有不限出口的 IPv6 masquerade 改写这类连接；OxiDNS 也要能返回 IPv6 地址（AAAA）。ConfigFlow 对防火墙、NAT 和 OxiDNS 只检查和提示，不会自动修改。

## 选择 IPv6 模式

- 模式与下方 YAML 双向同步：只改这个模式需要改的值，保留注释和其他字段。YAML 未填写 `ipv6` 或 `dns.ipv6` 时，按 Mihomo 默认值（`ipv6` 开启、`dns.ipv6` 关闭）显示并注明。
- 手写的组合不属于这三种模式时（例如 `ipv6: false` 而 `dns.ipv6: true`），显示「自定义」并说明原因，不会自动改写；选择任一模式后才改写这两项。
- 值来自 YAML 锚点、别名或合并时，需要改动这些共享值的模式不可选，请直接在 YAML 中修改。类型错误或 YAML 无法解析时，模式选择不可用，并就地显示原因。
- 选择任一 IPv6 模式且 DNS 使用 Fake-IP 模式时，自动补上缺失的 `fake-ip-range6: fc00::1/64`，已有网段沿用，并显示「IPv6 Fake-IP 网段」输入框。两个 IPv6 模式都显示输入框；输入框与 YAML 双向同步，只接受 `fc00::/7` 范围内的 IPv6 CIDR；格式错误或误填公网、链路本地地址时会提示并禁止保存发布，未提交的输入受离开保护。选择「关闭」会收起输入框并保留网段。不会改变 DNS 模式或开启 TUN；空草稿首次切换时使用实际默认模板。
- YAML 已处于某个 IPv6 模式却没有填写网段时（例如手写的配置），输入框显示默认值并注明尚未写入 YAML，上游路由暂不发布；编辑网段或重新选择模式后补齐。

## 需要完成的步骤

模式下方列出还要完成的步骤。每一步显示当前状态：通过的只占一行，有问题的直接写原因，没完成的给出按钮或链接。「关闭」不显示步骤。

| 步骤 | 出现在 | 状态来自 | 没完成时 |
| --- | --- | --- | --- |
| Mihomo 主机准备 | 两个 IPv6 模式 | 设备检查中的主机项：IPv6 地址、默认路由、转发与 RA、开机恢复等 | 写明原因；「检查设备」打开检查窗口，可在其中「补齐缺少的配置」 |
| 保存并发布 Mihomo | 两个 IPv6 模式 | 草稿是否已保存；设备检查比对已保存草稿与设备实际运行的 IPv6 设置；Mihomo 实际要收到的文件是否与上次成功发布的一致（与 Agent 页的同步状态用同一个比较，见下文「什么算待发布」） | 写明哪些设置不同或配置尚未发布，使用底部「保存并发布」；服务端在后台比较时显示「核对中」 |
| 上游路由发布 | 两个 IPv6 模式（IPv6 Fake-IP 路由、规则集 IPv6 网段在两个模式下都会发布） | 上游路由的待发布提醒 | 显示待处理的项数（暂时无法发布的也算在内），链接到对应路由器的预览发布；提醒的逐台说明只在发布栏和设备检查窗口显示，不在步骤里重复。没有路由器关联这台 Mihomo 时，「客户端也走 IPv6」提示需要关联，另一个模式只显示中性的「未关联」 |
| 路由器防火墙 / NAT | 两个 IPv6 模式 | 设备检查：与差异报告相同的同口转发判断（两个模式），以及客户端 Fake-IP 路径的 NAT 与防火墙结果（只在「客户端也走 IPv6」时检查） | 通过显示「无需处理」；有问题时写明原因，同口转发附可复制的放行命令 |
| OxiDNS 返回 IPv6 地址 | 「客户端也走 IPv6」，且关联路由器的 DNS 使用 OxiDNS | 路由器设置中的 DNS 设备 | 提示核对「优先 IPv4」、屏蔽 AAAA（类型 28）等设置，不做修改 |
| 验收 | 两个 IPv6 模式 | 保存的验收结果，按下文三项结果判断 | 直接显示三项结果和「验证连接与分流」；全部通过只占一行 |

- 步骤读取的是已保存的配置。有未保存的修改时显示「保存后检查」。
- 和 Agent 页的「IPv4 转发」一样，设备检查只在设备或配置变化时重新进行，平时显示上次的结果，并注明「设备检查于 12 分钟前，上游路由读取于 3 分钟前」。以下情况会重新检查：这台 Mihomo 上下线、换版本或设备记录变化；已保存的 Mihomo 配置变化（保存草稿后若内容有改动）；发布成功；关联的上游路由记录变化；从未检查过；以及点击步骤右上的「重新检查」。防火墙 / NAT 一步直接用设备检查的结果，不另外读取差异报告。
- 「上游路由发布」、发布栏和设备检查窗口的提醒只读取正在编辑的配置空间；其他空间关联同一设备的记录不计入数量，直达链接也只指向本空间的路由器。
- 「上游路由发布」使用待发布提醒的读取：路由器记录、配置空间修订号和 Agent 记录都没变时一直沿用上次读取；保存、发布成功或点击「重新检查」时重新读取路由器，读取失败的结果不沿用。
- **在路由器或 Mihomo 主机上直接做的修改不会自动发现**，处理完后点「重新检查」。
- 上次结果保存在 ConfigFlow 服务端，重启后仍可显示。重新检查失败（例如设备离线）时保留上次结果，并注明这次未能重新检查及原因；结果依赖的设备或配置已变化时注明是变化前的结果。设备离线时不会去连接它。这些读取都不写入设备。
- 从设备面板进入时固定检查该设备；从生成页进入且本配置空间有多台 Mihomo 时，需要先选择设备。原设备改绑、离线或被禁用时不会自动换成其他设备。
- 防火墙和 NAT 的命令只原样展示后端给出的内容；NAT 问题没有固定命令，需要按提示自行调整 masquerade 的出口接口。

## 使用流程

1. 在生成页的「Mihomo 基础配置」或 Mihomo 面板的设置中选择「IPv6 模式」，规则见上文。
2. 点击「保存草稿」后窗口保持打开，并提示保存成功，步骤随即按已保存的配置更新（内容有改动时重新检查设备）。可继续修改，或点击步骤右上的「检查设备」打开独立检查窗口。从设备面板进入时固定检查该设备；从生成页进入时选择本配置空间的 Mihomo 设备。检查是只读的，关闭窗口后保留 YAML 草稿。
3. 查看三项结果：**IPv6 网络、IPv6 节点连接、客户端分流**。通过的项目只占一行；需要处理的问题直接说明原因和下一步。页面不再展示逐条 RA、防火墙、NAT 或回程推演。预检发现地址和默认路由，只表示网络已就绪；实际连接通过需要运行验证。
4. 需要时点击「补齐缺少的配置」，仅处理 Mihomo 主机参数和开机恢复；这个入口不再写 ROS 路由。操作前重新核对配置、设备绑定和路由状态；实际草稿、目标设备或路由变更时停止。重复保存相同草稿、无关设备后台状态、路由列表返回顺序和 RA 有效期递减不会单独使检查失效。仅为已关联上游路由或启用 Linux 网关的设备自动开启转发。
5. 两个 IPv6 模式都按步骤中的「上游路由发布」到「上游路由 → 差异报告」查看 **IPv6 Fake-IP 分流路由**，核对网段、下一跳和状态。通过原有「预览发布」统一发布到 ROS。缺少稳定下一跳、网段冲突或读取失败时会阻止发布；只有「客户端也走 IPv6」要求 TUN。
6. 通过「保存并发布」把 YAML 应用到 Mihomo。确认这次发布成功、且这次发布的配置开启了 IPv6 后，后台自动验收该设备和这次发布的配置版本。保存草稿、网络补齐、待激活或失败的发布都不会被当作发布成功。
7. 发布栏直接显示同样的三项结果。节点或客户端待验证时，点击「验证连接与分流」；尚未配置客户端时，先在「检查设备 → 验收设置」选择独立检测客户端。未取得实测证据不显示通过；配置未应用时提示先「保存并发布」。「关闭」模式发布的配置没有 IPv6，发布栏只显示发布结果，不显示验收结果、「验证连接与分流」或「检查设备」提示；手动验收接口此时返回「未启用 IPv6，无需验收」。是否开启 IPv6 按这次发布的那一份配置判断，之后保存的草稿不影响。截图见 [Mihomo 面板：发布后验收](manual/mihomo-panel.md#发布后验收)。

## 路由由 ConfigFlow 统一管理

![上游路由中的受管 IPv6 Fake-IP 路由](img/guide/mihomo-ipv6-managed-route.png)

- **待添加**：预览发布后创建路由，并保存对象 ID 和配置记录。
- **已同步**：路由与当前保存的网段、下一跳一致，由 ConfigFlow 管理。重复发布不会重复添加。
- **沿用已有路由**：已有正确的手工或旧版路由，直接使用，不修改备注或接管归属；选择「关闭」时不会自动删除它。
- **待更新 / 待撤回**：改网段、选择「关闭」或 DNS 不再使用 Fake-IP 后，再到差异报告预览并发布；只调整已确认归属的受管路由。在两个 IPv6 模式之间切换不产生待发布项。
- **冲突 / 待确认**：地址不明确、网段重叠、受管对象被外部修改或读取失败时，保留现场并提示处理。

**防火墙提示**：设备经 ROS 同一 LAN 口转给 Mihomo 时，Mihomo 的回包不经过 ROS，ROS 会把同一连接的后续包判为 `invalid`。如果 IPv6 防火墙 forward 链在放行之前有「drop invalid」（RouterOS 出厂规则就有），新连接可能卡几秒甚至超时。下一跳是链路本地地址时，RouterOS 会发 ICMPv6 重定向，逐个建立连接时基本不卡；同时建立多个连接，或设备忽略重定向时，仍会卡住或超时。重定向只能部分缓解，不能依赖。提示文字与 IPv4 同口转发共用。差异报告检测到这种情况时，在「IPv6 Fake-IP 分流路由」中给出原因和一条可复制的放行命令（按 LAN 口进出放行，放在 `drop invalid` 之前），同时覆盖 IPv6 规则集路由。ConfigFlow 只提示，不修改防火墙，路由照常发布。设备检查对检查时已读取的规则做同样的判断，不另外连接路由器，结果显示在 IPv6 模式下方的「路由器防火墙 / NAT」一步。详见 [上游路由](manual/routers.md#ipv6-规则集路由-routeros)。

切换模式只修改草稿；ROS 上的受管路由要经过上游路由发布才撤回。在两个 IPv6 模式之间切换不改变路由。路由变更和原有发布共用状态复核、写后读取验证和失败补偿。自动 IP 规则同步不会顺带发布这些变更，出现 IPv6 差异时会暂停并要求手动预览。

规则集里的公网 IPv6 网段（如 Telegram 的 `IP-CIDR6`）由「上游路由 → IPv6 规则集路由」处理：IPv6 模式为「Mihomo 用 IPv6，客户端走 IPv4 分流」或「客户端也走 IPv6」（顶层 `ipv6` 开启）且有 TUN 时，经同一套预览发布指向这台 Mihomo，下一跳选择与 Fake-IP 相同；无法确定时只跳过这一项。自动规则同步会应用这些网段的增减。详见 [上游路由](manual/routers.md#ipv6-规则集路由-routeros)。

**待发布提醒**：保存草稿或保存并发布后，发布栏按路由器的实际状态提示，例如「上游路由「测试 ROS」有 2 项待发布」；设备检查窗口每次检查后也显示，并列出「IPv6 Fake-IP 分流路由：待添加」等项目。点「查看并发布」直接打开该路由器的差异报告和预览发布，确认后才写入。全部同步时不显示；读取失败显示「无法确认上游路由状态」和原因，不当成已同步。详见 [待发布提醒与直达链接](manual/routers.md#待发布提醒与直达链接)。

## 验收设置

默认执行 Mihomo 主机自检。在设备检查窗口底部展开「验收设置」，可以选择独立检测客户端和检测网址。

- 不配置客户端时，检查主机、DNS 和代理访问；「客户端分流」显示「未配置」，说明尚未配置检测客户端。主机自检通过不代表手机、电脑的流量已测过。
- 检测客户端必须是本配置空间中独立的在线 Linux Agent，需要位于 ROS 后面，并使用平时的 DNS 和默认网关。Mihomo 主机自身不作为独立客户端。界面不会自动选择；原设备离线、改绑或不支持检测时，需明确重新选择或改为仅检查主机。
- 检测网址留空时使用这次发布快照中的健康检查网址，没有设置则使用默认检测网址。自定义地址只接受不含账号密码的 HTTP 或 HTTPS 网址。
- 保存设置后，后续手动验证和发布后验收使用这些设置。配置客户端后会检查它的 DNS、实际访问及对应的 Mihomo 连接证据；缺少任何必要证据时保留未验证或提醒，不把主机结果代替客户端结果。

验收在后台执行，可以关闭检查窗口或离开页面。结果会保存，重新打开设备检查可读取；发布栏的自动结果始终对应那次发布，不会把之后编辑的草稿算进来。设备、配置版本或验收设置已变化时，旧结果不能用于证明当前状态，需要重新验证。

### 什么算待发布

判断「当前保存的配置是否已发布到这台 Mihomo」，只看 Mihomo 实际收到的文件（主配置、规则和订阅文件），与 Agent 页的同步状态用同一个比较，不看配置空间的版本号：

- 发布上游路由会把路由归属记录写回同一配置空间，修改 OxiDNS 等其他服务的设置也会让版本号增加，但 Mihomo 的文件没变。此时「保存并发布 Mihomo」仍显示「已发布」，「验证连接与分流」照常核对设备上的配置指纹，不需要再发布一次 Mihomo。
- 改了 Mihomo 的配置（例如规则、端口、DNS 或 IPv6 设置）并保存后，在重新发布前，「保存并发布 Mihomo」和验收的「IPv6 网络」都显示「待发布」。
- 版本号没变时直接判为已发布；版本号变了时，服务端在后台生成 Mihomo 要收到的文件，与上次成功发布比较，期间这一步显示「核对中」，几秒后更新。比较失败或没有可比较的发布记录时，不当成已发布。
- 先发布 Mihomo、再发布上游路由后，路由状态变了，发布后自动验收的结果会提示重新验证；重新检查并点击「验证连接与分流」即可，不会要求再发布 Mihomo。

示例截图见 [Mihomo 面板：发布后验收](manual/mihomo-panel.md#发布后验收)。

后端仍按规则顺序分析防火墙和 NAT，保留规则位置、条件和地址候选作为诊断依据，页面不再逐条展示这些内容。静态未知不会替代实际连通结论；发现确切问题时显示简短处理提示。检查不会自动关闭规则、添加 NAT66 或开启回流。

客户端验收同时核对本次请求的源地址、端口、网站、Mihomo 新连接与 ROS 连接记录。ROS 未启用连接跟踪、使用 `notrack` 或记录无法读取时，该段保留「未验证」；验收不会自行开启跟踪。当前请求级 IPv6 节点证据支持可明确核对实际远端的 SOCKS5/HTTP 节点；链式代理及无法取得证据的协议不冒充已通过。

## 自动修改的范围

- Linux Shell Mihomo Agent `1.8.50-go` 起支持。Docker 等不支持自动主机配置的环境保留只读说明。
- 检查实际上联网卡，补齐 IPv6 转发；依赖 RA 时，补齐该网卡的 `accept_ra=2` 和默认网关学习。已有静态默认路由不被改成 RA。
- 已有正确的用户 sysctl 配置保持原样，检查时核对来源文件及行号。仅缺失参数写入 `/etc/sysctl.d/99-configflow-ipv6.conf`，管理记录位于 Agent 配置目录的 `ipv6-readiness.json`。有后加载冲突、文件被外部修改或网卡身份变化时停止覆盖。
- 明确执行过准备后，Agent 开机恢复受管参数。启用 IPv6 Fake-IP 时，如果 Mihomo 早于主机 IPv6 就绪启动而缺少 IPv6 TUN 地址，会在地址和路由就绪后，对仍在运行且本地控制接口匹配的 Mihomo 热重载一次。不会启动已经停止的核心；等待超时、接口认证失败或配置不匹配会保留现状并给出检查提示。
- RouterOS 路由统一通过上游路由的差异报告、预览与发布管理。新路由优先使用唯一有效的链路本地地址（LLA），并带 RouterOS 出口接口，如 `fe80::1234%bridge`；没有 LLA 时才选同 LAN 的唯一可用 ULA。多个 LLA 无法唯一确定时停止。已有正确且下一跳仍属于这台 Mihomo 的路由继续沿用，不因优先级改变强制更换。只创建、更新或撤回本功能有完整管理记录的 IPv6 Fake-IP 路由。已有正确的非受管路由沿用；错误、停用、冲突路由保留并提示。
- DNS、DHCPv6 `use-peer-dns`、RA 广播 DNS、NAT66、防火墙、MSS 和自动回流只检查或提示，不作为 IPv6 模式的固定修改项。保持现有 IPv4 分流。

## 结果的含义

| 结果 | 帮你确认什么 |
| --- | --- |
| IPv6 网络 | 主机网络是否已就绪，或当前检测路径是否已实际连通 |
| IPv6 节点连接 | 检测网站能否通过节点访问，并有实际 IPv6 连接证据 |
| 客户端分流 | 独立客户端的请求是否经过 ROS、Mihomo 并到达检测网站 |

「待验证」会提示下一步操作，不展示一长串未确认的规则。确切的配置错误、发布缺失、连接失败及开机恢复缺项会归到相关结果中，直接说明处理方法。未配置检测客户端保持中性；「Mihomo 用 IPv6，客户端走 IPv4 分流」也照常检查 IPv4 客户端分流。旧版本、旧设备和中断的验收结果不能用于显示当前通过。

「配置开启」「发现持久化文件」「代理网站访问」「使用 IPv6 连接节点」「客户端全链路」「实际重启恢复」是不同证据。页面按检查范围显示结果，只有该范围所需项目都有通过证据时才显示通过。找到持久化文件不代表用户设备已经实测重启；网站访问成功也不能单独证明使用了 IPv6 节点或客户端路径正常。

把 IPv6 模式切换为「关闭」不会立即删除已有系统网络参数或路由；上游路由发布会按预览撤回本功能受管的路由。外部网络、运营商前缀分配、多默认路由和无法确认的防火墙策略需要单独处理；自动准备不会猜测或重建这些配置。

开发验证记录见 [PVE IPv6 验收](testing/ipv6-readiness-pve.md)。
