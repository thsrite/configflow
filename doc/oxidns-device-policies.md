# 客户端设备与 OxiDNS DNS 策略

入口：**当前配置 → 客户端设备**。也可以在 OxiDNS 面板点「客户端设备」，此时固定打开该 Agent 绑定的配置空间。

1. 在「未添加」中选择主路由（RouterOS / iKuai 4.x）看到的设备，点「添加」或勾选后点「添加所选」；也可以在「已添加」中手动输入 IPv4 / IPv6 地址及 CIDR 网段，例如 `192.168.50.0/24`、`2001:db8::/64`。从路由器添加时名称取设备主机名，DNS 策略默认智能分流。
2. 填写名称，按需选择 DNS 策略「默认」「智能分流」或「直连」。每一行修改后自动保存。
3. 名称立即生效，不需要发布。DNS 策略保存为草稿，勾选要发布的 OxiDNS 后点「发布」。发布沿用完整配置的校验、备份、应用和失败回滚流程，使用 Agent 支持的热重载或重启方式。

| DNS 策略 | 行为 |
| --- | --- |
| 默认 | 不单独设策略：落在已设策略的网段内时沿用该网段，否则保持默认分流。 |
| 智能分流 | 沿用当前配置的域名、IP 和默认分流规则；可作为「直连」网段中的例外。IPv4 地址同时是上游路由「策略路由」的来源，改动后需在上游路由页重新发布。 |
| 直连 | 保留公共查询记录、查询类型过滤、Hosts 和广告过滤，随后使用本地 DNS 上游，跳过分流及代理解析。 |

名称和 DNS 策略都清空后，设备从列表移除。名称在本配置空间共用：Mihomo 连接、数据统计和 OxiDNS 查询记录都按它显示。

例如 `192.168.50.50` 设为智能分流，`192.168.50.51` 设为直连。国内外如何划分仍由现有规则决定；代理侧需要先配置 Mihomo DNS，本地上游需要配置运营商或其他直连 DNS。设备策略不会自行配置 Mihomo、RouterOS 或 DHCP。

## 网段与优先级

- 规则重叠时优先匹配最具体的范围：单个 IP 优先于网段，小网段优先于大网段，与添加顺序无关。
- 例如 `192.168.50.0/24` 设为直连，`192.168.50.50` 设为智能分流，则 `.50` 使用现有分流规则，其余匹配该网段的设备直连。
- 智能分流也可以作为网段例外：`192.168.0.0/16` 直连、`192.168.50.0/24` 智能分流时，后者优先。
- 移除一条策略后，设备会落入剩余的更大网段策略；没有其他匹配才恢复默认分流。
- `192.168.50.51/24` 自动规范为 `192.168.50.0/24`。`/32` 和 `/128` 规范为单个地址，等价条目不能重复添加。
- IPv4 映射的 IPv6 地址及 `/96`–`/128` 网段会规范为 IPv4；更短的映射前缀不接受。IPv4 和 IPv6 分别匹配，`0.0.0.0/0`、`::/0` 可分别覆盖该地址族。

## 作用范围

- 上游路由「策略路由」的「来源设备」只读显示这些设备，并标出参与策略路由的智能分流 IPv4；在那里点「在客户端设备中管理」回到本页修改，改完后需在上游路由重新保存并预览发布。

- 设备属于 **配置空间**。从导航进入时使用侧栏选中的配置空间；从 OxiDNS 面板进入时使用该 Agent 绑定的配置空间，不切换全局空间。
- 同一配置空间的 OxiDNS 共用这份草稿。从导航进入时默认勾选所有在线的 OxiDNS，从 OxiDNS 面板进入时只勾选该设备；未勾选的设备保持现有配置。
- 发布的是该配置空间的完整已保存配置，包括其他已保存的改动。
- 设备列表分「已添加 / 未添加 / 已离线」三个标签（`?tab=new`、`?tab=offline` 可直接打开）。「未添加」和在线状态来自主路由读取快照，打开页面先显示上次结果，过期后后台更新，见下文「设备发现」；当前配置没有 RouterOS / iKuai 时只能手动添加，已保存设备的状态显示为未知。
- 「已离线」只列路由器判断为离线的已保存设备；近期见过、未知（例如不在路由器扫描的网段内、IPv6）和网段行都留在「已添加」。添加智能分流设备后，若已启用 RouterOS 策略路由，还需在上游路由重新发布。
- 每行单独保存：只有这一行在别处被改过时才会要求重新载入，修改其他设备或其他 OxiDNS 设置不影响。发布时如果草稿已在别处改变，会停止发布并要求重新载入。

## 设备发现（读取主路由）

`GET /api/client-devices/discovery?profile=<配置空间>`（或 `?agent=<OxiDNS Agent>`，与 `GET /api/client-devices` 相同的配置空间解析和登录要求）实时读取该配置空间中所有 RouterOS 与 iKuai 4.x 主路由，并发进行，每台最多约 20 秒。路由器读取快照按配置空间缓存在服务端内存中（最多 128 个空间，不落盘，服务重启后首次仍需读取）；一分钟内复用，超过一分钟先返回快照并标记 `stale`，页面再以 `?refresh=1` 后台重查。「重新载入」及固定 IP 操作后强制重查，刷新期间保留列表；路由器全部读取失败时保留上次可用快照，在 `refresh_error` 返回错误，自动重试至少间隔一分钟。并发首次读取或刷新共用同一轮扫描。路由器设置或凭据变化立即失效，固定 IP 写入前后均清缓存；名称、DNS 策略与 Agent 排除地址每次按最新配置合并，不缓存这些编辑数据。

```jsonc
{
  "success": true,
  "profile_id": "office",
  "state": "ok",            // ok | partial（部分路由器失败）| failed（全部失败）| unsupported（没有 RouterOS / iKuai）
  "message": "",            // unsupported 时为「需要在当前配置接入 RouterOS 或 iKuai 才能发现设备」
  "checked_at": "2026-10-25T10:46:34+08:00", // 当前显示的路由器快照采样时间
  "cached": false,          // 是否复用了上次快照
  "stale": false,           // true 时页面后台请求 ?refresh=1
  "refresh_error": "",      // 刷新失败但保留上次可用快照时的错误
  "sources": [              // 每台路由器一条
    {"id": "router_x", "name": "主路由", "type": "routeros", "ok": true, "error": "",
     "notes": ["账号缺少 test 权限，无法确认静态 IP 设备是否在线"],
     "policy_routing": true,  // 仅 RouterOS：已启用按来源策略路由（智能分流 IPv4 设备参与）
     "gateway": "192.168.0.8"} // 仅 policy_routing 为 true 时：代理网关 Agent 的 IPv4，策略路由不把它当来源；未关联为空
  ],
  "devices": [              // 每条已保存的行：{ip, name, mode} 加上下列字段
    {"ip": "192.168.0.133", "name": "摄像头", "mode": "direct",
     "presence": "online", "basis": "lease", "mac": "E0:BA:AD:94:F2:48", "hostname": "C6c_EZVIZ",
     "sources": ["arp", "lease"], "last_seen": 523, "router_id": "router_x",
     "discoverable": true}  // 这一行移除后是否会出现在 discovered（路由器、Agent 主机等为 false）
  ],
  "discovered": [           // 路由器看到、但没有自己那一行的 IPv4 地址，按地址排序
    {"ip": "192.168.0.147", "mac": "16:F7:C5:8A:16:A4", "hostname": "iPhone", "sources": ["arp", "lease"],
     "presence": "online", "basis": "arp", "last_seen": 286, "router_id": "router_x",
     "network": {"ip": "192.168.0.0/24", "name": "家里", "mode": "smart"}}   // 对它生效的网段策略，没有则为 null
  ]
}
```

- `presence`：`online` 在线、`recent` 近期见过（路由器记得它但无法确认）、`offline` 离线、`unknown` 未知；已保存的网段行为 `network`，IPv6 行为 `unknown`。
- `basis` 说明依据：`arp`（ARP 状态）、`lease`（DHCP 续租时间）、`probe`（经路由器主动确认）、`terminal`（iKuai 终端监控）、`stale`（只有未确认的 ARP 记录或租约）、`absent`（所有路由器都读取成功，地址在某台路由器扫描的局域网网段内，但没有出现）、`router`（路由器自己的地址）、`outside`（与 `unknown` 一起出现：地址不在任何路由器扫描的局域网网段内）。其他 `unknown` 的 `basis` 为空。
- `sources`：`arp`、`lease`（DHCP 租约）、`online`（iKuai 在线终端）。`last_seen` 是距上次 DHCP 通信的秒数，未知为 `null`。
- 已保存的单个 IPv4 是某台读取成功的路由器自己的地址（含管理地址）：`online`，`basis` 为 `router`，`router_id` 为该路由器。客户端把路由器当 DNS 转发时 OxiDNS 只看到路由器地址，这样的行不会被当成离线。
- 已保存的单个 IPv4 没有出现在任何路由器中：只有所有路由器都读取成功、所需的表都读到，并且地址落在某台路由器扫描的局域网网段内，才为 `offline`（`absent`）。网段外的地址（例如没开 DHCP 的服务器 VLAN、WireGuard 对端、其他设备后面的子网）为 `unknown`（`outside`）。有路由器读取失败，或 RouterOS 的 IP 地址、DHCP 服务、DHCP 租约表读取失败，或 iKuai 的 `lan` 读取失败时为 `unknown`，来源提示中会说明。
- `network` 只看设置了 DNS 策略（`mode` 非空）的网段行，取其中前缀最长的一条，与 OxiDNS 和 RouterOS 策略路由（`smart_sources`）实际生效的策略一致；只有名称、没有策略的网段行不会出现在这里。
- `discovered` 不含路由器自己的地址、路由器管理地址和本配置空间 Agent 主机的地址，也不含只有失败 ARP 记录（无 MAC、无租约）的地址。

### RouterOS 判断规则

只看局域网：启用的 DHCP 服务所在接口；没有 DHCP 服务时，改用配置了静态私有地址（RFC1918）的接口，排除动态地址（例如 DHCP 获取地址的 WAN）和接口列表 `WAN` 的成员。WAN 侧大量 `failed` ARP 记录不会出现。这些接口上 `/ip/address` 的网段就是判断离线的范围；其他接口（如只配静态地址的服务器 VLAN）上的已保存设备显示为未知。

1. ARP 状态 `reachable` / `delay` / `probe`：在线。
2. 租约 `bound` 且 20 分钟内续租过：在线（默认租期 30 分钟，在线客户端约每 15 分钟续租）。
3. ARP `failed` / `incomplete`：离线。
4. 租约错过续租（超过租期一半再加 5 分钟，至少 20 分钟）：离线。静态租约显示 `waiting` 而主机使用静态 IP 的情况不算错过续租。
5. 只剩 `stale` / `permanent` ARP 记录（RouterOS 中 stale 记录不会过期，常见于静态 IP 的虚拟机），或租约较新但没有 ARP：经路由器主动确认。在该接口上发 ARP ping（`POST /rest/ping {"address","count":"2","interval":"300ms","arp-ping":"yes","interface"}`，屏蔽 ICMP 的主机也会应答）：
   - 有应答：在线（`probe`）。
   - 两次 ARP ping 都没有应答：直接判为离线（`probe`）。同一网段内在线的主机必须应答 ARP，所以这条不再等 ARP 表变化；之后若有时间再读一次 ARP 表，`reachable` 仍会改判为在线。已在 RouterOS 7.24.5 CHR 上实测：不存在的地址无应答、判为离线，在线主机应答、判为在线。注意：处于深度休眠、暂时不应答 ARP 的设备可能因此显示在「已离线」，这一点尚未在真实设备上实测。
   - ARP ping 请求失败（例如该接口类型不支持 ARP ping）：改用普通 ping。有应答为在线；没有应答时再读一次 ARP 表：`reachable` 为在线，`failed` / `incomplete` 为离线，其余仍为近期见过。
   - 已保存的地址优先，每次最多确认 32 台、6 个并发。每个请求只用到截止时间前剩余的时间（单次最多 4 秒，不足 1 秒就不再发起），ARP ping 超时后不会再用普通 ping 重试同样长的时间；来不及确认的设备显示为近期见过。各表的读取同样只用剩余时间。这样确认阶段不会超过整台路由器的读取时限，已读到的 ARP 和租约不会因超时被丢弃。
6. RouterOS 的 `/ping` 需要用户组带 `test` 权限；没有时返回 HTTP 500 `not enough permissions (9)`，此时不再继续，这些设备显示为「近期见过」，并提示「账号缺少 test 权限，无法确认静态 IP 设备是否在线」。超时或超过上限的设备同样显示为近期见过。读取和确认都不修改路由器配置。

### iKuai 4.x 判断规则

接口形式已在 iKuai 4.0.314 上核对（测试数据 `backend/testdata/ikuai_clients_40314.json`）：列表用 `show`，参数 `{"TYPE":"data,total","limit":"<起始>,<条数>"}`，返回 `{"data":[...],"total":N}`，每页 1000 条。

- `monitor_lanip`（终端监控）中的地址为在线。名称取备注 `comment`、终端名 `termname`、主机名 `hostname` 中第一个非空值；只有 DHCP 客户端有 `hostname`，静态 IP 设备没有这个字段。终端监控只列出最近有流量经过路由器的设备（4.0.314 实测：客户端停止流量后 100–120 秒从列表消失，租约仍在），来源提示「按 2 分钟内经过路由器的流量判断在线」。
- `dhcp_lease` 只用于发现设备；不在终端监控中的地址为离线。`last_seen` 取距上次分配或续租的秒数（`end_time - start_time - timeout`，只用路由器自己的时钟；续租时 `start_time` 会更新）。读取失败只记为提示。
- `lan` 的 `ip_mask`（如 `192.168.77.1/255.255.255.0`）是路由器自己的局域网地址，不会出现在 `discovered` 中；它的网段也是判断离线的范围：已保存的地址只有在这些网段内、又不在终端监控中时才算离线。`lan` 读取失败时，未出现的已保存设备显示为未知，并提示「无法读取路由器的局域网地址，没有出现的已保存设备显示为未知」。
- 错误码（4.0.314 实测，很多错误响应也带 `"Result":10000`，不能据此判断为 3.x）：
  - `1001`：账号没有该功能的读取权限，`Label` 为功能名（如「终端监控IPv4」）；受限账号调用不存在的接口也返回 1001。
  - `1002`：账号没有执行（修改）权限。
  - `1003 Access denied`：固件没有这个接口（管理员账号调用不存在的 `func_name`）。
  - `1005`：登录时账号或密码错误。
  - `1008`：会话已过期，ConfigFlow 会重新登录一次再重试。
  - `3001`：action 或参数无效。
- 受限账号需要读取权限：终端监控IPv4（`monitor_lanip`，必需）和 DHCP 租约（`dhcp_lease`，权限提示中的功能名为「IPv4」）；`lan` 可选。

## 网络条件

设备需通过 OxiDNS 查询，并且 OxiDNS 能看到真实客户端来源 IP。可以由路由器 DHCP 统一下发 OxiDNS 地址，建议固定 DHCP 租约。若所有查询先由路由器转发，OxiDNS 可能只看到路由器的地址。

此功能控制 DNS 解析，不会撤销 RouterOS 全局真实 IP 代理路由，也不会拦截设备自行使用 DoH 或硬编码目标 IP。IPv4 与 IPv6 地址分别配置；地址变化后需要更新策略。

## 原生配置兼容

无需修改 OxiDNS 核心。ConfigFlow 使用原生 `client_ip` 匹配器，维护 `cf_device_policy` / `cf_device_direct` 两个插件和主处理链中的一个入口。直连使用独立执行链，不复用代理响应缓存，也不触发分流用的 RouterOS 动态规则。

仅对可识别的主处理链开放编辑：没有 include，`sequence_main` 每一步都有 `exec`、最后一步是 `goto china_dns` 或 `goto proxy_dns_seq`，`forward_local` 配有上游。插件命名冲突或设备策略片段被手动改动时，同样停止自动修改。拒绝时提示写明具体是哪一项，例如“主处理链 sequence_main 的最后一步是「accept」”；其他原生字段和附加文件保留。删除最后一条直连策略会移除专用插件及入口。

DNS 监听入口（`udp_server`、`tcp_server`、`quic_server`、`http_server`）按端口区分：

- 监听客户端 DNS 端口的入口必须以 `sequence_main` 为 `entry`。客户端端口指 53，以及主处理链入口自己监听的端口；IPv6、高可用虚拟 IP 的 `:53` 同样算。端口无法确认（例如用了环境变量）时也按客户端端口处理。不满足时提示入口名、监听地址和实际的 `entry`。
- 其他端口上的入口可以用独立的处理链：处理链不能直接或间接调用 `sequence_main`，用到的插件必须存在，也不能含未展开的环境变量。设备策略对这些入口不生效，接口在 `side_entries` 中返回 `{tags, listen, entry}`，客户端设备页列出提示。
- ConfigFlow 自己的节点测速入口不列出。托管入口（`cf_node_test_<ID>_*`）按 Agent 记录 `node_test_dns_endpoints` 中保存的插件定义逐项核对，记录属于当前配置空间、未删除且完全一致才算；被手动改过的按普通旁路入口提示。旧版手工创建的测速入口不看名字，同时满足两点才算：测速 DNS（`node_test_dns` 或自定义模式的服务器）正指向这个监听地址；入口只进一个 sequence，这个 sequence 只被这组入口使用、不再跳转到其他 sequence，用到的 forward 也只被它使用。
- 设备策略只改 `sequence_main` 和两个专用插件，旁路入口的插件原样保留。

可选真实核心验收：设置 `OXIDNS_TEST_BINARY` 指向本机 OxiDNS，运行 `backend/test_oxidns_device_policy_core.py`。测试仅启动临时本地 DNS 上游与核心，以 IPv4 / IPv6 客户端验证单 IP、网段、智能分流例外、嵌套网段和全地址族规则下的同域名查询互不串流；另有一项在旁边放一个测速专用入口，验证插入、修改、撤销设备策略时，主入口按设备分流，测速入口始终使用自己的上游。`scripts/tests/device_policy_side_entries_lab.py` 在 PVE 隔离实验网的容器里用真实核心重复这一流程。
